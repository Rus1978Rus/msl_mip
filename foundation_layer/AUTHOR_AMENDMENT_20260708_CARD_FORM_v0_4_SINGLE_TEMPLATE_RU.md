============================================================
СУТЬ ПОПРАВКИ
============================================================

1. ШАБЛОН КАРТОЧКИ ЗНАКА — ОДИН. Отдельный тип/шаблон
   «тонкой карточки» (THIN_HOMOGLYPH_CARD) НЕ вводится.
   Формулировка автора: «у нас есть утверждённый шаблон карточки
   знаков, другого не будет; если знак не совершает какого-то
   действия, прописанного в шаблоне, там пойдёт прочерк или
   пустота».

2. Тип знака различается полем META.CARD_TYPE со значениями:
     FULL      — знак с собственной функцией/жизнью;
     HOMOGLYPH — знак-двойник, существующий как маска другого
                 знака.
   Отсутствие поля = FULL (legacy v0_3, совместимо с D1).

3. Для CARD_TYPE: HOMOGLYPH графы, не имеющие содержания у
   знака-маски, заполняются NOT_APPLICABLE / прочерком;
   минимумы шаблона на такие графы не распространяются
   (HOMOGLYPH_FILL_RULE в шаблоне v0_4). Прочерк — тоже знание:
   «у этого знака нет собственной жизни, только чужая форма».

============================================================
ЧТО ОСТАЁТСЯ В СИЛЕ (ядро D2 не тронуто)
============================================================

- Гомоглиф входит в рантайм ТОЛЬКО через СВОЮ карточку
  (ARCH_DECISION_HOMOGLYPH_VIA_CARD_ONLY; решено кодом:
  scan_signs строит реестр из visible_form карточек, записи
  CONFUSABLES в реестр не попадают).
- Запись CONFUSABLE в карточке канона = отношение/провенанс,
  НЕ рантайм-вход.
- Обязательные для гомоглифа: CANONICAL_TARGET (последовательность,
  D6), ссылка на карточку канона, VERIFICATION_SNAPSHOT.

============================================================
ПРИЧИНА
============================================================

Термин «тонкая карточка» возник в конвейере прошлой сессии и
попал в текст решения, но автором как отдельная сущность не
вводился и не признан. Один шаблон = один парсер, один путь
рантайма, один стандарт будущей библиотеки; «неприменимо» —
законное содержание графы, а не повод для второго шаблона.

============================================================
СЛЕДСТВИЯ ДЛЯ ПЛАНА РЕАЛИЗАЦИИ (мигпакет, «шесть шагов»)
============================================================

- Шаг 2 (отдельный шаблон THIN_HOMOGLYPH_CARD) — ОТМЕНЁН.
  Вместо него: правка шаблона v0_4 (CARD_TYPE: FULL/HOMOGLYPH,
  HOMOGLYPH_FILL_RULE, поля CANONICAL_TARGET/CANON_CARD_REF
  для гомоглифов).
- Шаг 3 (парсер): второй dataclass не нужен; читается CARD_TYPE
  и поля гомоглифа. Механика ИСПОЛНЕНИЯ карточек HOMOGLYPH в
  module_engine (у двойника нет персонального matcher) —
  уточняется при реализации, как и было помечено в D2.
- Масштаб (тысячи двойников) закрывается НЕ карточками, а
  normalization-слоем (РЕШЕНИЕ 1); карточки HOMOGLYPH — выборочно,
  по атакам (дисциплина входа как в FO-реестре); черновики
  выводимы автоматически из зафиксированных источников Unicode.
