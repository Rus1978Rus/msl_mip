3. Q3 РАСКОЛ (поле/тип) — РЕШЁН ПО КОДУ (VERIFY_BEFORE_TRUST)
──────────────────────────────────────────────────────────────────
Ревьюеры разошлись: ~3 «ПОЛЕ» (проще, не плодит сущности),
~3 «ОТДЕЛЬНЫЙ ТИП» (масштаб), 1 (doc 30) СИНТЕЗ.

ПРОВЕРКА ПО КОДУ (решающая):
  scan_signs: sign_chars = {c.visible_form: c for c in cards}
  — реестр рантайма = ТОЛЬКО visible_form самих карт.
  load_card: confusables грузятся в card.confusables (вложенный
  список), НЕ в sign_chars.
СЛЕДСТВИЕ (VERIFIED): если ／ записан ПОЛЕМ внутри карточки SOLIDUS,
  scan_signs его НЕ УВИДИТ (if ch in sign_chars не сработает — ／ не
  visible_form ни одной карты). Чтобы ／ попал в детекцию рантайма,
  у него ДОЛЖНА быть СВОЯ карточка с visible_form=／.

ВЫВОД: «поле vs тип» — ЛОЖНАЯ ДИЛЕММА. Правильно И ТО, И ДРУГОЕ, но
для РАЗНОГО (синтез doc 30, подтверждён кодом):
  - ПОЛЕ в карточке канона = ОТНОШЕНИЕ/провенанс: «／ — confusable
    моего знака /, verified NFKC/UTS#39». Документирует связь.
  - ТОНКАЯ КАРТОЧКА гомоглифа (visible_form=／) = РАНТАЙМ-ВХОД:
    попадает в sign_chars, наследует риск канона, scan_signs ловит.
Формула: FIELD = relation/provenance ; THIN_CARD = runtime entry.

Это разрешает раскол не голосованием, а архитектурным фактом. И это
ПРЯМО реализует R-B (гомоглиф входит как знак только через карточку):
тонкая карточка — и есть та карточка, поле — только документация связи.

7. НОВЫЕ ОБЯЗАТЕЛЬНЫЕ ПУНКТЫ (из MISSED, сошлись независимо)
──────────────────────────────────────────────────────────────────
M1. ПРАВИЛО КОНФЛИКТА авто vs override (назвали 5 из 7). Проект-
    предложение (Qwen + doc 30):
    - авто нашёл, override нет → авто побеждает (добавляется);
    - override есть, авто нет → HOLD_FOR_REVIEW (пометка
      MANUAL_OVERRIDE_UNVERIFIED, не тихо принимать);
    - оба, разный risk → override побеждает (автор видит контекст),
      но с флагом OVERRIDE_DISAGREEMENT → ревью.
M2. UNICODE VERSION в карточке ОБЯЗАТЕЛЬНА (7/7): NFKC/skeleton
    меняются между версиями; без версии верификация невоспроизводима.
    (у нас уже есть sources/17.0.0 + version pinning — совместимо.)
M3. ВАЛИДАТОР/ЛИНТЕР карточек сообщества: при PR запускать норм-слой,
    требовать verification_snapshot ИЛИ override_justification, иначе
    блок PR. Это будущая CI-часть библиотеки-стандарта.
M4. SKELETON ≠ НОРМАЛИЗАЦИЯ (doc 30, UTS#39 прямо): skeleton только
    для внутреннего сравнения, НЕ хранить как «канонический текст».
M5. ONE-TO-MANY маппинг: NFKC даёт не codepoint, а ПОСЛЕДОВАТЕЛЬНОСТЬ
    (ﬁ→f+i). Форма должна допускать canonical_target_SEQUENCE, не
    только один codepoint. (связано с офсет-развилкой норм-слоя.)
