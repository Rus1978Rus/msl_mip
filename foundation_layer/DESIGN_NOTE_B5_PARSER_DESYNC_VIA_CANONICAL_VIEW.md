============================================================
§1. ЧТО ТАКОЕ B5 (из карточки BOM, RISK_CASE_006 PARSER_DESYNC)
============================================================
Невидимка класса-138 ставится там, где ОДИН парсер её срежет, ДРУГОЙ оставит →
две системы «видят» разные строки одного потока → рассинхрон представления.
Пример: pay<BOM>pal.com — строгий декодер даёт paypal.com, наивный оставляет
другой токен. Кто из них принимает решение о безопасности — расходится.
ЖЕЛАЕМЫЙ уровень: РЕАЛЬНАЯ (вектор реален). РАНТАЙМ-СТАТУС: PENDING.

============================================================
§2. ПОЧЕМУ РАНТАЙМ СЕЙЧАС СЛЕП (честно)
============================================================
Карточка фиксирует: рассинхрон парсеров — свойство ВНЕШНИХ систем, не наблюдаемо из
одной входной строки текущим детектором. Детектор видит ОДНУ строку; desync — про ДВЕ
системы. За работающий контракт не выдаётся, риска не эмитит.

============================================================
§3. КЛЮЧ: ГАРД МАТЕРИАЛИЗУЕТ ОБЕ СТОРОНЫ DESYNC ВНУТРИ СЕБЯ
============================================================
D-GUARD-DESIGN (APPROVED, §3 «два артефакта») по КОНСТРУКЦИИ строит:
  - original       — бит-в-бит = что видит НЕстрипающий (наивный) потребитель;
  - canonical_view — производный вид = что видит СТРИПАЮЩИЙ/нормализующий потребитель;
  - биективная карта позиций original↔canonical_view (P7).
=> Внешнее «свойство двух систем» превращается во ВНУТРЕННЮЮ наблюдаемую разницу двух
   артефактов ОДНОЙ строки. Desync наблюдаем БЕЗ внешних систем — как расхождение
   original ↔ canonical_view в security-значимой единице (токен/хост/граница меняет
   смысл между видами).

Это и есть то, что заметил reconcile: B5 закрывается не новым детектором «двух систем»,
а сравнением двух видов, которые гард и так обязан построить.

============================================================
§4. ПОЧЕМУ ФРОНТ СЕЙЧАС ВЫКЛЮЧЕН (заземлено кодом)
============================================================
Инкремент-1 гарда (msl_mip_runtime.py, class_guard_annotate, VERIFIED прогоном 2026-07-20):
  строка ~573: canonical_view = text   (IDENTITY — производный шаг заглушён, P6)
  строка ~574: position_trace = "identity"
=> original == canonical_view всегда → разница пуста → desync-фронт выключен КОРРЕКТНО
   (инкремент-1 сознательно report-only, identity-вид; см. D-GUARD-IMPL-PLAN P5/P6).
B5 «включается», когда canonical_view станет НАСТОЯЩИМ strip-видом (derive ≠ identity).

============================================================
§5. ЧТО НУЖНО, ЧТОБЫ B5 СТАЛ НАБЛЮДАЕМ (спецификация фронта)
============================================================
(1) DERIVE: canonical_view из identity → реальный strip/normalize-вид класса-138
    (что увидел бы стрипающий парсер). ТОЛЬКО как ВИД (D2: original бит-в-бит неизменен,
    никогда не strip вслепую; DEFAULT_IGNORABLE ≠ SAFE_TO_DELETE — P4/P5 доказали
    разрушение эмодзи/арабского). Property-based, контекст-свободно (Join_Control:
    ZWJ/ZWNJ не трогать).
(2) COMPARE: детектор рассинхрона = функция(original, canonical_view, position_trace).
    Сигнал НЕ на «есть невидимка» (это уже presence-witness), а на «удаление её МЕНЯЕТ
    security-значимую единицу»: reconstructed токен/хост/граница в canonical_view ≠ в
    original. Ровно тот removal-probe-приём, что уже есть в _reconstructed_context /
    _detect_context_at (sequence_engine) — но теперь как ЯВНОЕ сравнение двух видов.
(3) УРОВЕНЬ: desync-сигнал = отдельный РИСК-СЛОЙ НАД гардом (D3 5/5: гард presence,
    не risk). Куда его класть по трёхуровневой шкале (ВОЗМОЖНАЯ vs РЕАЛЬНАЯ) — это
    O1-территория (рантайм-риск-мэппинг), НЕ решается тут.
