- КОМБИНАТОРНЫЙ ВЗРЫВ НЕВИДИМОК: чтобы посчитать «миллион невидимок», система обязана их

  Ловится реконструкцией (_demask) на уровне ПРАВИЛА, но приём — первая проверка.
- КЛАСС 138, трёхуровневый принцип, витнес-рамка — не пересматриваются.

ИЗМЕРЕННЫЙ ДЕФЕКТ (профилирование нашего кода 2026-07-21 — субстрат, не на ревью):
  ХОТСПОТ невидимого флуда: `_detect_context_at` (sequence_engine.py:494) — 6000 ZWSP →
    57.6 с; вызван 18000 раз (3× на знак), каждый вызов O(n) → O(n²). + `_demask` (стр.283)
    ещё 4.6 с (9× на знак). ВЕРДИКТ флуда = pass (гигантский невидимый флуд молча очищается —
    дыра витнеса вдобавок к DoS).
  ХОТСПОТ слэш-флуда: `_find_literal_matches` (стр.62) — 8000 «/» → 8.3 с; генератор
    (стр.140) вызван 31 996 000 раз ≈ n²/2. + `_attach_source_offsets` (стр.177).
  ВАЖНО: сам solidus_matcher ЛИНЕЕН (0.7 с) — знак не виноват; O(n²) в SEQUENCE-слое.
  ЧЕСТНЫЙ ВВОД (для калибровки, из черновика): тестовый фишинг ~40 Б; длинный URL ~65 Б;
    русский абзац ~200+ Б; код ~2 КБ. Батарея ZWSP — короткие, ОДИНОЧНЫЙ невидимый.

КРИТИЧЕСКИЙ ФАКТ (почему дизайн судится ДО кода):
- Рубеж встаёт на входе `analyze()` — ПЕРЕД sequence-анализом, от которого зависит
  верифицированный ZWSP (батарея 21/21). Рубеж, срабатывающий на честном коротком вводе,
  сломает 21/21. Обязан бить ТОЛЬКО по патологии.
- Лимит-число нельзя брать «на глаз»: мал → режет честный ввод (100 Б зарезали бы
  собственный тестовый фишинг); велик → DoS проезжает. Плюс: голый лимит T не чинит
  алгоритм — вход чуть-меньше-T всё ещё O(T²).
- Уже есть родственное: гард-инкремент-1 несёт `_GUARD_MEMBER_CAP=4096` + TRACE_TRUNCATED
  (report-only, НЕ в вердикт-пути). Родственно, но это shadow-поле, не DoS-рубеж входа.

============================================================
§2. ВОПРОС РЕВЬЮЕРАМ (двигатель круга — дизайн, «как обойдут / где сломается»)
============================================================
Спроектировать input-guard режима A (байтовый якорь + плотность) так, чтобы он: закрыл
измеренный DoS (O(n²) на невидимом/слэш-флуде) И дыру флуд→pass, НЕ сломав верифицированный
ZWSP (21/21) и честный короткий ввод, остался в витнес-рамке (свечение СВОРАЧИВАЕТ, не
авто-блок), прошёл r>g и САМ не создал поверхность (рубеж-как-DoS, обход рубежа плотностью).
По КАЖДОМУ измерению §3 — ответ + «где дыра / чем обходится».

============================================================
§3. ИЗМЕРЕНИЯ ДИЗАЙНА (на ревью)
============================================================
G1. МЕСТО И МЕХАНИЗМ РУБЕЖА. Где встаёт (вход analyze(), ДО scan_signs/sequence)?
    «Взвесить по ходу / early-abort» vs «проверка длины/плотности до анализа» — при том что
    в режиме A строка уже целиком в памяти (вставка). Что достаточно и не трогает sequence-путь?

G2. ЛИМИТ: байт-потолок vs ПЛОТНОСТЬ (невидимое:видимое) vs оба. Точное правило, которое
    (а) отбивает 6000-ZWSP флуд, (б) НИКОГДА не бьёт по 21 кейсу батареи + честному вводу
    (40 Б фишинг, 200 Б русский, 2 КБ код). Порог по контексту (машинный низкий / CJK высокий) —
    как выразить без ложных тревог? Число — замером или формулой?

G3. РУБЕЖ ДОСТАТОЧЕН ИЛИ ЧИНИТЬ АЛГОРИТМ? Голый лимит T → вход чуть-меньше-T всё ещё O(T²)
    (десятки КБ² = сотни млн операций). Кандидаты (не ограничивать):
      G3a. только рубеж (early-abort) — принять, что до лимита O(n²) допустим;
      G3b. рубеж + фикс O(n²) в `_detect_context_at`/`_find_literal_matches` (общие факты один раз);
      G3c. рубеж достаточно МАЛ, чтобы O(T²) был приемлем.
    Что выбрать по r>g и не-контаминации (G3b трогает верифицированный relation-путь)?

G4. ВИТНЕС-РАМКА ПРИ ЗАВАЛЕ. Флуд был pass → должен стать? Свечение СВОРАЧИВАЕТ в ОДНУ
    сводку («⚠ N невидимых, X% ввода, HOLD»), не N подсветок, НЕ авто-блок. Как выразить
    уровень (HOLD/witness) без превращения в судью? И флуд→pass: под-пороговый флуд обязан
    хотя бы витнесить, не молча pass — где граница «завал» vs «плотность-сигнал»?

G5. НЕ-КОНТАМИНАЦИЯ ZWSP (главный риск). Как СТРУКТУРНО гарантировать, что рубеж НИКОГДА не
    срабатывает на 21 кейсе батареи + честном вводе, и батарея 21/21 + mutation 5/5 + oracle
    переприйдут? Acceptance-гейт: батарея + новые flood-bounce тесты + FP-тесты честного ввода.

G6. ОТНОШЕНИЕ К СУЩЕСТВУЮЩЕМУ. (i) Гард-cap `_GUARD_MEMBER_CAP`/TRACE_TRUNCATED (report-only) —
    рубеж поглощает / переиспользует / рядом? (ii) DENSITY_ANOMALY черновика (плотность как
    СИГНАЛ, контекстный) vs INGESTION (байт-якорь, early-abort) — один слой или два разных
    (рубеж рубит, плотность витнесит)? (iii) _demask ловит взрыв на уровне правила — как рубеж
    с этим сожительствует?

G7. ОХВАТ. Режим A только (интерактивный текст). Режим B (файлы: zip-бомбы, скрытое в
    структуре) — ЯВНО вне круга (отдельный крупный фронт). Что минимально-полезно для A?

G-OTHER (открытая графа): ревьюер называет измерение вне G1–G7 с ответом по §4. Если рубеж
    как идея неверен (напр. защита от DoS не место рантайма) — сказать прямо (LOOPHOLE).

============================================================
§4. КРИТЕРИИ ОЦЕНКИ (по каждому измерению)
============================================================
(а) НЕ ЛОМАЕТ ВЕРИФИЦИРОВАННОЕ — ZWSP 21/21 + mutation 5/5 + oracle переприйдут; рубеж не
    бьёт по честному короткому вводу.
(б) ЗАКРЫВАЕТ ИЗМЕРЕННЫЙ DoS — невидимый/слэш-флуд не доводит до O(n²); флуд→pass закрыт.
(в) r>g — рубеж дёшев (O(1)/O(n) один проход), не растит g; алгоритм-фикс (если брать) оправдан.
(г) ВИТНЕС-РАМКА — свечение сворачивает в сводку, HOLD/witness, НЕ авто-блок; последнее слово человеку.
(д) РЕАЛИЗУЕМ — детерминированно, тестируемо, герметично; порог обоснован (замер/формула).
(е) НЕ СОЗДАЁТ НОВОЙ ПОВЕРХНОСТИ — сам рубеж не DoS; обход плотностью/чуть-ниже-порога закрыт;
    свёртка свечения не теряет реальную атаку под сводкой.
Ревьюер: по каждому измерению — 6 отметок + BASIS; для G2 (лимит) и G3 (рубеж vs алгоритм) —
ЯВНЫЙ выбор + почему; RANKED_OUTCOME; RECOMMENDATION (скелет рубежа) как рекомендация, не статус;
явно — рубеж верен или LOOPHOLE.
