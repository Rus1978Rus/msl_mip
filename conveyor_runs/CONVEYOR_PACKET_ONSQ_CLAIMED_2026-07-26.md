============================================================
§1. ФАКТ (измерено на живом ядре 2026-07-26, ПОСЛЕ D-ONSQ-FIX — данные, спорить только замером)
============================================================
slash-флуд `'/'*n` (ASCII-солидус карта): 1500→0.21с; 3000→0.64с (×3.1); 6000→2.53с (×4.0);
  12000→11.1с (×4.4). ×≈4 на удвоение = O(m²), D-ONSQ-fix'ом НЕ затронут (иной хотспот — верно).
АТРИБУЦИЯ (cProfile, slash×6000):
  ДОМИНАНТА — `claimed`-покрытие: генератор `covered = any(c_start <= idx and end <= c_end
    for c_start, c_end in claimed)` в цикле по матчам — **17 997 000 вызовов, 1.85с** (O(m²): для
    каждого из m матчей скан всех ранее принятых интервалов). `_find_literal_matches` в целом 1.73с.
  ВТОРАЯ — `_attach_source_offsets`: **1.32с**, O(m×s) (матчи × статусы).
СЕМАНТИКА `claimed` (вычитка, КРИТИЧНО для эквивалентности): `covered` = «существует РАНЕЕ ПРИНЯТЫЙ
  интервал, ПОЛНОСТЬЮ СОДЕРЖАЩИЙ [idx,end]». НЕ overlap, НЕ union. Контрпример слияния (замерен
  логикой, подтверждён Kimi+GPT): claimed {(0,5),(4,10)}, запрос (2,8) → по одиночным НЕ содержится,
  по СЛИТЫМ содержится → union даст неверный True. Интервалы поступают в порядке ПРИОРИТЕТА
  КАНДИДАТОВ (pool отсортирован по убыванию длины sequence), НЕ по source-позиции → «монотонный
  указатель, т.к. матчи по возрастанию start» НЕ эквивалентен (доказано: порядок вставки ≠ source).
ЦЕЛЬ: near-linear + ДОКАЗУЕМО ZERO-DELTA (тот же набор covered → тот же набор матчей → тот же отчёт),
  differential-гейтом. Образец процесса — D-ONSQ-FIX (reference-oracle + 5888+3000 differential).

============================================================
§2. ВОПРОС РЕВЬЮЕРАМ
============================================================
Выбрать структуру/алгоритм для containment-запроса «существует принятый интервал с start≤idx И
  end≥end», ОНЛАЙН в порядке приоритета кандидатов, ДОКАЗУЕМО эквивалентную текущему `any(...)`,
  делающую путь near-linear, не сломав батареи. По КАЖДОМУ V1–V5 — позиция + «где риск тихой дельты».
  Это круг ПРОИЗВОДИТЕЛЬНОСТИ: любое изменение набора матчей/вердикта = провал.

============================================================
§3. ИЗМЕРЕНИЯ НА РЕВЬЮ
============================================================
V1. CONTAINMENT-СТРУКТУРА. Кандидаты: (A) отсортированные starts + max-end augmentation (запрос:
    среди интервалов со start≤idx есть ли max-end≥end); (B) interval tree; (C) Fenwick/segment-дерево
    по сжатым координатам; (D) frontier недоминируемых интервалов. Требование: ONLINE-вставка в
    priority-порядке (не offline-сортировка), точная containment-семантика (не overlap/union),
    удаление внутренних записей только с доказательством неизменности будущих запросов. Явный выбор.
V2. `_attach_source_offsets` O(m×s). Индексация по offset вместо матчи×статусы. Чинить в этом круге
    или третьим? Доказать эквивалентность (тот же attach-результат, тот же порядок).
V3. DIFFERENTIAL-ГЕЙТ. Reference-oracle `_find_literal_matches` (старый как test-only), сравнение
    ПОЛНОГО отчёта побитово + структурные counters (containment-запросов ≤ O(m log m)) + scaling
    T(2n)/T(n) ≤ 2.5 + slash-корпус + фаз. По образцу gate_onsq_zero_delta (5888 offset + 3000 fuzz).
V4. ПОРЯДОК. `claimed` управляет тем, КАКИЕ матчи приняты, и финальной сортировкой матчей. Любая
    смена порядка приёма/финального списка = дельта. Сохранить точный priority-порядок обработки +
    финальную сортировку (source-pos, убыв. длины, стабильность Python sort).
V5. ОБЛАСТЬ. Только `claimed` (V1) в этом круге, `_attach_source_offsets` (V2) — отдельным? Или оба?
    Минимально-достаточно для near-linear на slash/видимо-символьных флудах.
V-OTHER: если подход неверен (напр. долг снимается сменой самого matcher-контракта) — сказать прямо
    (LOOPHOLE). Подтвердить, что рубеж Mode A этот фикс НЕ заменяет (12КБ<cap, но 11с).
