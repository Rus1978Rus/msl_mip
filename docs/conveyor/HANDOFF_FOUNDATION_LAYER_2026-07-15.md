============================================================
0. ОТКРЫТИЕ, ИЗ КОТОРОГО ВСЁ ВЫРОСЛО
============================================================
КОМБИНАТОРНЫЙ ВЗРЫВ НЕВИДИМОК. Одно слово, визуально единственное, машинно —
миллионы неотличимых форм. paypal (6 букв, 7 щелей), 8 видов невидимых по щели →
9^7 ≈ 4,7 млн двойников, ВСЕ выглядят как paypal. sberbank → ~387 млн. Ловится
НЕ списком (бесконечен), а МЕХАНИЗМОМ реконструкции (_demask снимает все невидимые
→ обнажает оригинал → одно правило ловит все миллионы). Уже реализовано в детекторе.

СЛЕДСТВИЕ-УГРОЗА (найдено автором): чтобы система поняла «тут миллион невидимок»,
она должна их ВПУСТИТЬ и посчитать. Впустить миллион = атака уже сработала
(память/время съедены ДО вердикта). DoS через объём. «7 vs миллион» — две большие
разницы на впуске.

============================================================
1. БАЙТОВЫЙ ЯКОРЬ — РУБЕЖ НА ФИЗИЧЕСКОМ ДНЕ
============================================================
ИЕРАРХИЯ (снизу вверх, чем выше — тем больше обмана):
  БАЙТ     — физическая реальность. НЕ маскируется. «Байт сам мета» — не требует
             интерпретации, чтобы быть посчитанным.
  КОДПОИНТ — интерпретация байтов (можно спрятать: percent-encoding).
  ФОРМА    — как выглядит (грим: гомоглиф).
  СМЫСЛ    — что значит в контексте (ZWSP друг/враг).

КЛЮЧ: невидимость живёт ВЫШЕ байта. ZWSP невидим на экране, но его 3 байта
(E2 80 8B) физически в потоке. Спрятать знак от глаза можно; спрятать его ВЕС —
нельзя. Байты взвешиваются ДО любой интерпретации.

ПОРЯДОК ЗАЩИТЫ:
  1. взвесить (байты — физический якорь) — считать ПО ХОДУ чтения;
  2. перевалил лимит → early abort: СТОП, не дочитывая (миллион не входит целиком,
     рубится на первых сотнях);
  3. разбирать содержимое ПОТОМ — уже в безопасном объёме (обман есть, но не может
     сработать: объём ограничен).

ПРИНЦИП: приём ЕСТЬ первая проверка. Вердикт «слишком много» выносится В ПРОЦЕССЕ
чтения, не после полного приёма. Граница защиты — на самом впуске, не после анализа.
Это ФИЗИЧЕСКИЙ якорь защиты — как BY_CODE якорь истины: то, что нельзя подделать,
потому что оно ДО подделки.

============================================================
2. ЛИМИТ — ОТНОСИТЕЛЬНЫЙ, НЕ АБСОЛЮТНЫЙ; БАЛАНС, НЕ МИНИМУМ
============================================================
ЧИСЛО. Порядок — ДЕСЯТКИ КБ (10-50 КБ), НЕ сотни байт. Честный ввод уже весом:
тестовый фишинг проекта (paypal.com.security-check.ru/verify) ~40 Б; длинный URL
~65 Б; русский абзац ~200+ Б (кириллица ×2 байта); код ~2 КБ. Лимит 100 Б зарезал
бы собственную тестовую ссылку. Лимит = ПОТОЛОК реального использования + воздух,
НЕ «чем меньше тем лучше» (мал → режет честное; велик → DoS). Точное число — замером.

ПЛОТНОСТЬ, НЕ СЧЁТ (поправка автора: «7 или миллион — образно»). Абсолютное число
не судит. Судит СООТНОШЕНИЕ невидимого к видимому в КОНТЕКСТЕ (сквозной принцип —
контекстность):
  - машинный контекст (домен/код/id): порог низкий (даже единицы подозрительны);
  - CJK/typography: высокий (переносы легитимны);
  - плотность (невидимого ≥ видимого) → аномалия независимо от числа;
  - расхождение «мало видимого / много сырого веса» → сам по себе сигнал.
Человеку — ОТНОСИТЕЛЬНЫМ языком: «невидимого больше, чем видимого» / «аномальная
плотность для домена». Число показать, но не судить по нему.

СВЕЧЕНИЕ СВОРАЧИВАЕТ, НЕ ПЕРЕЧИСЛЯЕТ. При завале НЕ подсвечивать 100k знаков (flood
= оружие против свечения: утопить человека шумом, чтобы пропустил настоящую атаку /
отключил систему). Сводка: «⚠ N невидимых знаков (X% ввода). Нормальный текст так не
выглядит. Возможно: атака, мусор, повреждение. HOLD.» Одно число + вывод, не N
подсветок.

============================================================
3. ВХОД МНОГОЛИК — РУБЕЖИ ПО ТИПУ (не выплеснуть ребёнка)
============================================================
ОШИБКА, КОТОРУЮ АВТОР ОСТАНОВИЛ: свести вход к одной трубе «текст ≤ N байт» →
зарежет файлы ИЛИ оставит дыру бомб. Вход НЕ монолит.

── A. ИНТЕРАКТИВНЫЙ ТЕКСТ (вставка / набор) — ТЕКУЩИЙ РЕЖИМ ──
  - вставка: риск ПОТЕРИ невидимок при copy-paste (при вставке в окно часть не
    копируется — та же невидимость работает ПРОТИВ на входе; ср.
    SEMANTIC_INVISIBLE_LENGTH_WITNESS в Notarius);
  - набор руками: невидимок почти нет, завал физически не грозит;
  - байт-якорь ПРЯМОЙ, лимит-страница (десятки КБ) верен ЗДЕСЬ.
  СТРОИМ СЕЙЧАС. Простой байтовый лимит на детектор — дёшево, конкретно, закрывает
  реальную DoS-дыру, стоит на неподделываемом дне.

── B. ФАЙЛОВЫЙ ВХОД — КРУПНЫЙ ФРОНТ (наравне с гомоглифами) ──
  БАЙТЫ ФАЙЛА ≠ БАЙТЫ ТЕКСТА. Формат — контейнер: .docx = zip+XML; .pdf = бинарь
  (текст в потоках); .html = текст+теги; картинка = пиксели. Байт-якорь на файл =
  лимит на РАЗМЕР ФАЙЛА (от гигабайта), но анализ невидимок — по ИЗВЛЕЧЁННОМУ
  тексту, не по байтам контейнера.
  НОВЫЕ ВЕКТОРЫ (которых нет в тексте):
    - ZIP-БОМБА: мал файл (.docx 1 МБ) → распаковка в терабайты → лёг при извлечении.
      Нужен лимит на РЕЗУЛЬТАТ извлечения, не только на файл;
    - БЕЗОПАСНОЕ ИЗВЛЕЧЕНИЕ: бомба не должна сработать при распаковке;
    - СКРЫТОЕ В СТРУКТУРЕ: невидимки/атака в тегах, метаданных, потоках — извлекать
      ВЕСЬ текст, включая скрытый, иначе атака проедет в метаданных;
    - разные форматы = разные парсеры = разные риски.
  ЭТО ОТДЕЛЬНОЕ БОЛЬШОЕ НАПРАВЛЕНИЕ (парсинг форматов, безопасное извлечение,
  защита от бомб). Крупный фронт НАРАВНЕ с ГОМОГЛИФАМИ. НЕ строить сейчас, НЕ
  сводить к текстовому лимиту.

── C. ПОТОКИ / API — БУДУЩЕЕ ──
  Читать ОКНОМ фиксированного размера, всё в память не брать. Отдельный продукт
  (пакетный/сервисный режим), если понадобится. НЕ сейчас.

============================================================
4. РОДСТВЕННЫЕ РУБЕЖИ ВХОДА (все про вход, разной глубины)
============================================================
  - INGESTION (байт-якорь) — не дать завалить объёмом (самый низ, при чтении,
    early abort);
  - INTEGRITY — не потерять/добавить при передаче (copy-paste потеря невидимок;
    ср. Notarius INVISIBLE_LENGTH_WITNESS);
  - DENSITY_ANOMALY — аномальная плотность как сигнал (уже в анализе, относительная,
    контекстная).
  Три рубежа: от «физически впустить» до «оценить впущенное».

============================================================
СЛЕДУЮЩИЕ ШАГИ / СТАТУС
============================================================
СЕЙЧАС (дёшево, конкретно, после ZWSP): байтовый лимит на входе детектора (режим A).
  Стоит на неподделываемом дне, закрывает найденную DoS-дыру.
КРУПНЫЙ ФРОНТ (наравне с гомоглифами, НЕ сейчас): ФАЙЛОВЫЙ ВХОД — парсинг форматов,
  безопасное извлечение, защита от zip-бомб, скрытое в структуре.

СВЯЗЬ: метафора «грим на юникоде» (байт — под гримом и под лицом, самый низ);
  контекстность (плотность аномальна относительно контекста); система оповещения
  (свечение сворачивает, не флудит; лимит = природа инструмента для человека, не
  пакетного сканера); Notarius (целостность входа).
РЕЕСТР ФРОНТОВ: гомоглифы · файловый вход · PHAGO_NATURE · (input-guards INGESTION).

════════════════════════════════════════════════════════════════
БЛОКЕР — _domain_prefix: чёрный список → позитивная выборка
════════════════════════════════════════════════════════════════
НАХОДКА (три ревьюера, первый круг). _domain_prefix обрезал обрамление
домена по чёрному списку _STRIP_OUTER (фиксированный набор пунктуации).
Любой символ ВНЕ этого списка — markdown-звёздочка *, тире U+2014,
тильда ~, pipe |, полноширинная кавычка U+FF02 и т.п. — прилипал к
домену. Пример: `*gоog／le.com*` — после снятия маски label становится
`*gоogle.com*` (или после старой логики — `*gоog` / `le.com*` по
частям), в любом случае лишний символ остаётся ВНУТРИ метки, проверка
`ch.isalnum() or ch == "-"` на этот символ проваливается → домен не
распознаётся → тихий FREE_TEXT. Реальный обход HOST/HIGH-вердикта, не
краевой случай — блокирует READY_TO_SAVE.

РЕШЕНИЕ (не AUTHOR_DECISION в строгом смысле — обязательное
исправление корректности, не решение по вкусу). _domain_prefix
переписан с чёрного списка на ПОЗИТИВНУЮ выборку: находит первый
максимальный непрерывный блок домено-подобных символов — буква
ЛЮБОГО алфавита (Unicode-осведомлённая проверка `ch.isalnum()`,
поэтому IDN/гомоглиф-атака кириллицей по-прежнему ловится — это то,
что детектор ДОЛЖЕН ловить, а не исключать), цифра, дефис, точка — и
отбрасывает всё остальное. Закрывает весь класс обхода одним
изменением, а не патчами по символу.

Побочный эффект: этот же позитивный скан САМ ПО СЕБЕ подхватывает
старую функцию отреза хвоста (P5: `/`, `?`, `#`, `:`, пробел) — ни
один из этих символов не входит в allow-list, скан останавливается на
них естественным образом. Отдельный цикл `for sep in (...)` убран как
избыточный.

ПРОВЕРКА. Весь предыдущий gate (25 прежних кейсов: P2/P3/P4/P5,
D-DET-1, D-DET-2, FP-guard, zero-width boundary) прогнан ПОСЛЕ правки
— 25/25 без изменений в ожидаемых вердиктах. Плюс 5 новых кейсов на
сам обход (звёздочка, тире, тильда, pipe, полноширинная кавычка) — все
теперь дают HOST/HIGH вместо прежнего тихого FREE_TEXT.

D-DET-3 — ЛОЖНЯКИ СКЛЕЙКИ: ДОКУМЕНТИРОВАТЬ, НЕ ЧИНИТЬ
════════════════════════════════════════════════════════════════
РЕШЕНИЕ АВТОРА. Позитивная выборка выше — эвристика, не полноценный
URL-парсер. Склейка левой и правой части токена вокруг маски
(left_part + right_part, механика D-DET-1) может дать ложный HOST на
двух НЕ связанных фрагментах, если результат синтаксически похож на
домен. Это признаётся и документируется как известное поведение
эвристики, НЕ как дефект, требующий немедленного исправления.

ПРИМЕРЫ (реальный вывод детектора, не предположение — прогнано
07-12):
  - `my-host／name.com` → HOST/HIGH. «my-host» и «name.com» — два
    самостоятельных фрагмента (например, из разных предложений или
    случайно соседствующих слов), которые после снятия маски
    склеиваются в синтаксически корректный `my-hostname.com`.
    Настоящей подмены домена здесь может не быть.
  - `example.com,／test` → HOST/HIGH (НЕ HOST/PATH — уточнено прогоном:
    запятая останавливает позитивный скан ДО «test», поэтому проверка
    «склеенное = домен» просто заново находит левый домен
    `example.com` и даёт HOST; «test» молча выпадает из рассмотрения).

ПОЧЕМУ НЕ ЧИНИТЬ СЕЙЧАС. Убрать этот класс ложняков означало бы
полноценный URL/токен-парсер с пониманием границ «слово / слово»
против «домен», что выходит за рамки текущего грубого детектора (Г1
исторически и есть «грубый», см. исходный докстринг
`_detect_context_at`). Правильный инструмент — отдельная итерация
детектора, не патч поверх позитивной выборки.

ЗАКРЕПЛЕНО В GATE. `tests/gate_bare_domain_detector.py`, секция

fixed` — оба примера закреплены ассёршенами на НАБЛЮДАЕМЫЙ вердикт
(не на «правильный»), чтобы будущее изменение эвристики проявилось
здесь явно, а не расползлось незамеченным.

ДОПОЛНЕНИЕ 2026-07-12 (второй круг, узкий круг по _domain_prefix).

ДВА ХВОСТА — ОТЛОЖЕНЫ НА v0.5, ДОБАВЛЕНЫ В GATE КАК KNOWN
════════════════════════════════════════════════════════════════
ХВОСТ 1 — уже-punycode вход вне активного справочника.
  Пример: `gоog／le.xn--zckzah` → FREE_TEXT/NONE (тихий пропуск) —
  проверено на пришпиленном тестовом TLD-наборе, НЕ содержащем
  `xn--zckzah`. `_is_tld` сперва проверяет метку как есть (не найдена),
  затем пробует `.encode("idna")` (для уже-ASCII `xn--...` строки не
  меняет её), тоже не находит. Это зависимость от ПОЛНОТЫ активного
  справочника, а не отдельный баг детектора: в проде (live IANA fetch
  или встроенный fallback ~200 записей) современные punycode ccTLD
  почти наверняка присутствуют. Помечено как известное, не чинится в
  этом круге.

ХВОСТ 2 — дефис на краю метки.
  Пример: `-example.com／x` → PATH/MEDIUM. Проверка метки
  `all(ch.isalnum() or ch == "-" for ch in lbl)` не учитывает ПОЗИЦИЮ
  дефиса — RFC 952/1035 запрещают дефис в начале/конце метки, текущий
  код это не проверяет, поэтому `-example` проходит как валидная
  метка. Не чинится в этом круге — записано как известное отклонение
  от строгого RFC.

БЛОКЕР → D-DET-4 — ВЕДУЩИЙ СТРУКТУРНЫЙ СИМВОЛ ПРОГЛАТЫВАЕТСЯ
════════════════════════════════════════════════════════════════
НАХОДКА (узкий круг). Позитивная выборка (FIX_FIRST_ROUND1) пропускает
ВСЁ до первого доменного символа и НЕ различает обёртку от структурного
разделителя. Ведущий @ (email/mention) и / (путь) исчезают бесследно.

Измерено (старое чёрным списком → новое позитивной выборкой без D-DET-4):
  #example.com／x   FREE_TEXT → PATH/MEDIUM
  /example.com／x   FREE_TEXT → PATH/MEDIUM
  @example.com／x   FREE_TEXT → PATH/MEDIUM
  :example.com／x   FREE_TEXT → PATH/MEDIUM

Нарушенный принцип: WRAPPER ≠ STRUCTURAL_SEPARATOR. Позитивная выборка
имела право пропустить обёртку (скобка, кавычка, звёздочка), но НЕ имела
права молча отбросить структурную границу.

РЕШЕНИЕ АВТОРА D-DET-4. Ведущие / \ ? # : @ — HARD_STOP: если такой
символ встречен ДО начала доменного блока, _domain_prefix возвращает
пустую строку (у токена нет доменного префикса). Остальную внешнюю
пунктуацию (обёртки) по-прежнему пропускаем.

  _LEADING_STRUCTURAL_STOPS = frozenset("/\\?#:@")
  while i < n and not (token[i].isalnum() or token[i] in ".-"):
      if token[i] in _LEADING_STRUCTURAL_STOPS:
          return ""
      i += 1

Это НЕ возврат чёрного списка: список пунктуации бесконечен, список
структурных границ — ЗАКРЫТ и уже имеет смысл в спецификации (path,
query, fragment, port, authority/email). Мы не гадаем «что добавит
атакующий», мы называем «что структурно значимо».

ПРОВЕРКА (измерено ПОСЛЕ правки, escape-строки где нужна однозначность
байтов):
  - четыре структурных кейса #, /, @, : → FREE_TEXT (были PATH/MEDIUM);
  - пять обходов-обёрток *, тире, ~, |, ＂ → HOST/HIGH (целы, обёртка ≠
    структурный разделитель);
  - базовые gоog／le.com, приме／р.рф → HOST/HIGH (не задеты).
Добавлено 4 gate-кейса (секция [D-DET-4]).

1.2 — ИСПРАВЛЕНИЕ ФОРМУЛИРОВКИ (документация врала, код верен)
════════════════════════════════════════════════════════════════
НАХОДКА (узкий круг). Везде, где написано «буква ЛЮБОГО алфавита» —
это ложь. Правда: «символы, для которых str.isalnum() = True».
Combining marks (Unicode-категории Mn/Mc) её НЕ проходят: IDN-домен на
деванагари с огласовкой (bharat.bharat, кодпоинты базовых букв U+092D
U+0930 U+0924 с огласовкой U+093E) под маской -> FREE_TEXT, потому что
U+093E DEVANAGARI VOWEL SIGN AA (категория Mc) даёт isalnum()=False, и
позитивная выборка обрывается сразу после базовой буквы. То же для
арабских диакритик, ивритских огласовок, NFD-разложенной латиницы.

СТАТУС. Это НЕ регрессия и НЕ баг кода: старый чёрный список оставлял
combining mark в строке, но неизменённая проверка метки
(all(ch.isalnum() or ch == "-")) всё равно её отвергала — итог тот же
FREE_TEXT. Меняется ТОЛЬКО документация: она обещала больше, чем код
делает.

РЕШЕНИЕ. Формулировка исправлена в: докстринге _domain_prefix
(sequence_engine.py), заголовочном комментарии детектора,
AUTHOR_DECISION FIX_FIRST_ROUND1 (через настоящий документ — см. ниже),
карточке (LIMITATION_STATEMENT). Точная формулировка везде:
«поддерживаются символы, для которых str.isalnum() истинно (буквы и
цифры Unicode), плюс дефис и точка; combining marks — НЕ поддерживаются
(isalnum()=False), это известное ограничение». Закрытие combining marks
требует полноценной IDNA/NFC-канонизации кандидата целиком — вне scope
грубого детектора, отдельное будущее решение.

ЗАКРЕПЛЕНО В GATE. Кейс с деванагари+огласовка (строка построена из
escape-последовательностей ради однозначности байтов) как
known_limitation → FREE_TEXT.

ПОЧЕМУ не отдельная ось. Отдельный путь к финальному вердикту — это ровно

на будущее, чтобы к RLO не изобретать боковой путь.

D-INV-3 (форк 2 — ПУСТОЙ КАНОН): ЯВНЫЙ enum TARGET_KIND
════════════════════════════════════════════════════════════════
Когда у знака нет канона-кодпоинта, это выражается ЯВНЫМ enum
TARGET_KIND: EMPTY_SEQUENCE. НЕ пустой строкой, НЕ "NULL", НЕ U+0000.

ПОЧЕМУ. Пустое/отсутствующее поле TARGET неотличимо от «забыли заполнить /
парсер не прочитал / target неизвестен» — это ТИХИЙ ПРОХОД, тот же класс,
что ловили в детекторе весь день. Явный enum делает «канона нет»
НАМЕРЕННЫМ и проверяемым, а не совпадающим с ошибкой заполнения.

TARGET_KIND (enum): CODEPOINT | EMPTY_SEQUENCE | CLASS.
  CODEPOINT      — канон есть, TARGET обязателен (мимикрия: ／→U+002F).
  EMPTY_SEQUENCE — канона-кодпоинта нет (разрыв/пустота); TARGET опущен.
  CLASS          — канон = класс грубого фильтра; TARGET несёт имя класса.

════════════════════════════════════════════════════════════════
РЕШЕНИЕ D-GUARD-1 — ИНВАРИАНТ НА ФИНИШЕ (ЗАКОН СОХРАНЕНИЯ РИСКА)
════════════════════════════════════════════════════════════════
В analyze(), ПОСЛЕ most_severe и ПЕРЕД возвратом, выполняется НЕЗАВИСИМАЯ
проверка РЕЗУЛЬТАТА. Она читает только: финальное действие,
seq_out.relation_verdicts (источник истины оси маски) и — по D-GUARD-2 —
validation_warnings карточных рёбер. Она НЕ повторяет путь агрегации,
поэтому НЕ дублирует его хрупкость (это принципиально: второй ручной
путь агрегации был бы вторым местом, где всё может сломаться так же).

ИНВАРИАНТ. Если в relation_verdicts есть хоть один risk_level HIGH или
CRITICAL — финальный вердикт НЕ может быть PASS. Нарушение означает, что
вердикт маски не дошёл до финального действия: путь оборван.

МЯГКОЕ ПРАВИЛО. MEDIUM relation-вердикт при финале PASS — это метка
INTEGRITY_CONCERN, НЕ violation (не роняет, не блокирует; сигнал к
вниманию).

ПОВЕДЕНИЕ ПРИ НАРУШЕНИИ — ГИБРИД (осознанный):
  - В БОЮ (обычный прогон): вердикт НЕ меняется. Автор — единственная
    инстанция, имеющая право переопределить вердикт; сторож НЕ
    самоуправствует. В отчёт добавляется запись INTEGRITY_VIOLATION с
    деталью (какое ребро/relation_id, какой контекст, какой risk_level,
    какой финал), и прогон помечается PASS_WITH_INTEGRITY_VIOLATION.
  - В СТРОГОМ РЕЖИМЕ (env MSL_MIP_GUARD_STRICT=1, для гейтов/разработки):
    то же нарушение РОНЯЕТ прогон исключением IntegrityViolation.
    Регрессия, обрывающая путь маски, не проходит в разработке молча.

ПОЧЕМУ ГИБРИД, А НЕ АВТО-ПОВЫШЕНИЕ. Автоматически поднять вердикт до
HOLD в бою означало бы дать сторожу право переписывать вывод системы на
основании эвристики о самом себе. Это нарушает
AUTHOR_DECISION_STATUS_AUTHORITY. Сторож обязан КРИЧАТЬ, а не ТИХО
ЧИНИТЬ: в бою он делает нарушение видимым (метка + деталь), в разработке
— не пропускает регрессию (падение). Решение о смене вердикта остаётся
за автором.

РЕАЛИЗАЦИЯ (msl_mip_runtime.py):
  - _relation_actions(seq_out) — путь маска→действие вынесен в
    модуль-уровневый шов (был инлайн), чтобы chaos-гейт мог имитировать
    обрыв, НЕ трогая relation_verdicts.
  - _integrity_check(final_action, seq_out, cards) — сам инвариант
    (D-GUARD-1 + D-GUARD-2). Возвращает (violations, concerns).
  - class IntegrityViolation — исключение строгого режима.
  - analyze() зовёт проверку после most_severe; в строгом режиме и при
    наличии violations — raise; иначе кладёт integrity_status
    (OK / INTEGRITY_CONCERN / PASS_WITH_INTEGRITY_VIOLATION) и списки в
    отчёт. print_report печатает статус, если он не OK.

ГРАНИЦЫ (что НЕ сделано этим решением):
  - Детектор Г1, карточка ／, существующие гейты — НЕ тронуты.
  - Инвариант ловит «relation_verdicts говорят HIGH, а финал PASS». Он
    СЛЕП к «relation_verdicts были ошибочно опустошены ДО analyze()»

    сохранение риска от источника истины к финалу, а не целостность
    самого источника. Обрыв, опустошающий сам список, — предмет

РЕШЕНИЕ D-GUARD-2 — ОЖИВИТЬ validation_warnings (НЕ УДАЛЯТЬ)

Поле validation_warnings НЕ удаляется — оно ПОДКЛЮЧАЕТСЯ к инварианту

ПРАВИЛО. В _integrity_check строится карта активных рёбер, несущих
load-time validation_warning (по ключу visible_form + relation_id из
загруженных карточек). Если у активного ребра стоит validation_warning

не обрыв пути и не угроза сама по себе; это сигнал, что карточка обещает
защиту, которой код не даёт (класс SC1/SC2 аудита — например опечатка в

роняет прогон даже в строгом режиме; роняют только violations D-GUARD-1.

РЕЗУЛЬТАТЕ прогона, там же, где живёт инвариант, и по той же гибридной

       queue_for_review, сторож МОЛЧАЛ, хотя HIGH занижен. Это не «закон

════════════════════════════════════════════════════════════════
РЕШЕНИЕ D-GUARD-3 — СРАВНЕНИЕ СЕРЬЁЗНОСТИ, НЕ БУКВАЛЬНЫЙ PASS
════════════════════════════════════════════════════════════════
Сторож сравнивает СЕРЬЁЗНОСТЬ финала с минимумом, требуемым риском
relation-вердикта, а не проверяет равенство «== pass»:

  MEDIUM relation  → минимум queue_for_review
  HIGH relation    → минимум hold_pending_review
  CRITICAL relation→ минимум hold_pending_review
  NONE / LOW       → минимума нет (не проверяется)

Если severity(semantic_action) < severity(минимум для риска) → это
INTEGRITY_VIOLATION (а не только при финале pass). Каждое нарушение
несёт required_action, чтобы D-GUARD-4 мог поднять эффективный вердикт.
Так ловится HIGH→pass, HIGH→log_only, HIGH→queue — весь класс
занижения, а не единственная точка.

УСТОЙЧИВОСТЬ К ФОРМЕ risk_level. Значение нормализуется
str(...).strip().upper(), поэтому "high" / " HIGH " / "High" / enum
сравниваются одинаково. НЕИЗВЕСТНОЕ значение risk_level → CONCERN
(D-GUARD-3-UNKNOWN), НЕ молчаливый пропуск: «не знаю уровень» обязано
быть видимым, а не проглоченным (та же дисциплина, что ACK_GAP_TRIVALENT
UNVERIFIABLE ≠ пропуск).

СУТЬ

Варианты решения не ВЫБИРАЮТСЯ голосованием ревьюеров — они
ВЫМИРАЮТ под проверкой. Каждый круг конвейера спрашивает не
«какой вариант лучше», а «как этот вариант обойдут / чем он
ломается». Что не пережило проверку — отсекается доказательно.
Что дожило — доживает с ИЗВЕСТНЫМИ границами, а не как компромисс.

КЛЮЧЕВОЙ ВОПРОС-ДВИГАТЕЛЬ: «КАК ЭТО ОБОЙДУТ?»
Без него круг вырождается в спор о вкусах, и варианты НЕ убывают —
они накапливаются, а автор выбирает по интуиции. С ним каждый круг
уменьшает пространство решений.

════════════════════════════════════════════════════════════════
ТРИ ИСХОДА КРУГА (любой круг заканчивается одним из них)
════════════════════════════════════════════════════════════════

1. ОТСЕЧЕНИЕ — доказана дыра, вариант выбывает безвозвратно.
2. СИНТЕЗ — берётся сила обоих вариантов, выбрасывается слабость
   обоих; рождается третья конструкция, которой не было на входе.
3. ЛАЗЕЙКА — вскрыт дефект, которого не было ни в одном варианте
   (он жил в самой постановке). Круг повторяется на новой основе.

════════════════════════════════════════════════════════════════
КОГДА ПРИМЕНЯТЬ (порог стоимости)
════════════════════════════════════════════════════════════════

ПРИМЕНЯТЬ — развилки СРЕДНЕЙ стоимости и выше, где ошибка:
  - ТИХАЯ (не падает, не краснеет — молчит годами),
  - ОТЛОЖЕННАЯ (проявится не сейчас, а под атакой/нагрузкой),
  - ДОРОГАЯ (переделка тянет за собой смежное).
  Типовые места: детекторы, схемы данных, границы безопасности,
  публичные контракты, форматы, которые попадут к третьим лицам.

НЕ ПРИМЕНЯТЬ — дёшево-обратимые решения: имена, стиль, порядок
  секций, всё, где ошибка ГРОМКАЯ и чинится за минуту. Там это
  самоедство: два круга ревью на одну строку не окупаются.

ЧЕСТНАЯ ЦЕНА: метод дорогой. Два круга конвейера могут уйти на ОДНУ
  строчку логики. Оправдано ТОЛЬКО асимметрией ущерба: если ошибка
  дешевле проверки — проверка не нужна.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GATE_MUST_BE_HERMETIC:
  Гейт НЕ имеет права зависеть от внешних источников (сеть, живой
  реестр, изменяемый кэш, часы, случайность). Один и тот же код на одном
  и том же входе обязан давать один и тот же вердикт КАЖДЫЙ раз,
  независимо от того, доступна ли сеть и что она вернула.

  Живой справочник — для РАНТАЙМА. Пришпиленный — для ГЕЙТА.

  Гейт, зависящий от сети, — не гейт: он даст зелёный на СЛОМАННОМ
  коде, если сеть «подсказала» правильный ответ, и красный на РАБОЧЕМ
  коде, если сеть подвела. Это молчаливая деградация, а не тестовый
  сигнал. «Зелёный 20 раз» при живой сети НЕ доказывает корректность —
  доказывает лишь, что сеть в тот момент отвечала.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ДОКАЗАННАЯ ПРИЧИНА (не гипотеза)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Цепочка касания сети:
  gate_solidus_scheme.py спавнит msl_mip_runtime.py на КАЖДЫЙ кейс →
  runtime при старте зовёт dot_matcher.get_compound_suffix_source() и
  get_single_tld_source() → public_suffix.load_compound_suffixes() /
  load_single_tlds() → urllib.request.urlopen(publicsuffix.org /
  data.iana.org, timeout=3). Плюс gate_relation_verdict_step4.py →
  process_sequence → _assess_relation_risk → sequence_engine._tlds() →
  та же load_single_tlds().

Конкретный флип-кейс (измерено, не предположено):
  «paypal.com.security-check.ru» (gate_solidus_scheme, «dot substitution»)
    TLD-набор С 'ru'    → domain_separator + RISK_CASE_002 → HOLD (верно)
    TLD-набор БЕЗ 'ru'  → file_extension, без риска        → PASS (тихий
                          зелёный на том, что должно флагироваться)
  Частичный/битый/протухший ответ IANA, где 'ru' выпал, молча красит
  гейт зелёным. Это и есть молчаливая деградация.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
МЕХАНИЗМ ГЕРМЕТИЗАЦИИ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Флаг окружения MSL_MIP_HERMETIC_TLD (public_suffix.py): при установке
load_compound_suffixes() и load_single_tlds() ПРОПУСКАЮТ сеть и кэш и
возвращают встроенные (in-repo) EMBEDDED-наборы — детерминированный,

по умолчанию (флаг снят) не меняется: live → cache → embedded, как в
проде. Рантайм честно печатает HERMETIC-режим (не врёт про «нет сети»).

Способы пришпиливания по гейтам:
  - подпроцессный гейт (spawns runtime): MSL_MIP_HERMETIC_TLD="1" в env
    подпроцесса (gate_solidus_scheme);
  - in-process гейт: os.environ до первого вызова, ИЛИ прямой пин

Гейт без внешних источников вовсе (gate_english_only — только чтение
файлов) герметичен по построению, флаг не нужен.

БЛОК SIGN_RELATIONS — СТРУКТУРА
════════════════════════════════════════════════════════════════

ГДЕ ЖИВЁТ. Новый блок в карточке знака-маски. У обычного знака блока
НЕТ — карточка остаётся как есть (D-REL-1: каждый знак — просто знак).
Блок появляется ТОЛЬКО когда знак реально связан отношением, заведённым
ЯВНО (не авто-выведенным).

ОДНО РЕБРО (минимальная форма, D-REL-2):
  SIGN_RELATIONS:
    RELATION_001:
      RELATION_TYPE: <CONFUSABLE_OF / NFKC_MAPS_TO / VISUAL_MIMIC_OF>
      TARGET: <кодпоинт или последовательность канона, напр. U+002F>
      CONTEXT_SCOPE: <один или несколько из:
        URL / HOST / PORT / PATH / EMAIL / IDENTIFIER / IDN / CODE /
        FREE_TEXT / ANY>
      VERIFICATION_STATUS: <VERIFIED / CANDIDATE / MANUAL_OVERRIDE>
      RUNTIME_EFFECT: RELATION_ONLY

  RUNTIME_EFFECT=RELATION_ONLY — зашитый инвариант: ребро сообщает
  «похож на такой-то знак в таком-то контексте» и НИЧЕГО про риск.
  Риск решается НЕ здесь (D-REL-4).

CONTEXT_SCOPE — ПОЯСНЕНИЕ (расширен по конвейеру):
  URL        — url целиком
  HOST       — доменная часть (атака gοοgle.com с греч. o — ловится тут)
  PORT       — часть порта
  PATH       — путь после хоста
  EMAIL      — адрес почты
  IDENTIFIER — идентификатор/handle
  IDN        — международные доменные имена (Punycode/Unicode-домены)
  CODE       — исходный код
  FREE_TEXT  — свободный текст
  ANY        — контекст не важен (использовать ОСТОРОЖНО: ANY означает
               «маска везде», высокий риск ложных срабатываний —
               применять только когда связь действительно контекст-
               независима, напр. невидимый управляющий символ)

# ARCH_DECISION: ФОРМА КАРТОЧКИ v0_4 (ADDITIVE-DUAL)

**Статус:** AUTHOR_DECISION (принято ПАКЕТОМ)
**Дата:** 2026-07-07
**Автор решения:** Руслан Малявский (AUTHOR_DECISION_STATUS_AUTHORITY)
**Тип:** решение о форме карточки знака
**Основание:** конвейер CARD_FORM_UPDATE_v0_1, 7 ревьюеров.
Интеграция: INTEGRATION_CARD_FORM_UPDATE_v0_1_RU.md

---

## ПРИНЯТЫЕ РЕШЕНИЯ (D1–D7)

**D1 — COMPAT = DUAL. 5 готовых карточек НЕ мигрируют.**
Форма обновляется до v0_4 как ADDITIVE-DUAL. Блок CONFUSABLES в 5
готовых карточках (. / 💀 ☠ @) семантически переопределяется:
«исчерпывающий список» → «ручной OVERRIDE поверх авто-слоя».
Карточки валидны как есть, ручной труд миграции = 0. Основание:
7/7 ревью + совпадает с 6/6 ревью норм-слоя.

**D2 — ГОМОГЛИФ: поле=отношение, тонкая карточка=рантайм-вход.**
Разрешено КОДОМ (не голосованием): scan_signs строит реестр из
visible_form карт (проверено: sign_chars = {c.visible_form: c}),
confusables в реестр НЕ попадают. Значит:
  - ПОЛЕ в карточке канона = документация связи «／ confusable /».
  - ТОНКАЯ КАРТОЧКА (visible_form=／) = вход в рантайм, наследует
    риск канона, scan_signs ловит.
Это буквально реализует R-B (гомоглиф входит как знак только через
карточку). Исправляет ошибку PA3 (склонялся к «только поле» — код
показал, что поле не заводит знак в scan_signs).
[ПРИНЯТО; механика тонкой карточки уточняется при реализации.]

**D3 — VERIFICATION = ГИБРИД.** Слой (NFKC/skeleton UTS#39) =
источник истины, логика не дублируется в карточках. Карточка
кэширует СНИМОК верификации как провенанс (unicode_version,
nfkc_canonical, uts39_confusable, verified_at). Валидатор
перепроверяет. Основание: 7/7.

**D4 — MINIMUM_5 СНЯТЬ.** «Минимум 5 confusables вручную» = рудимент
квадратичной модели, вреден (добор «для формы» → ложные связи).
Замена: «авто из слоя + опц. ручные override, МИНИМУМ 0. Ручной
override обязан нести BASIS + verification_status». Основание: 7/7.

**D5 — ПРАВИЛО КОНФЛИКТА авто vs override.** Консервативное:
  - авто нашёл, override нет → авто побеждает (добавляется);
  - override есть, авто нет → HOLD_FOR_REVIEW + пометка
    MANUAL_OVERRIDE_UNVERIFIED (не принимать тихо);
  - оба, разный risk → override побеждает (автор видит контекст),
    но флаг OVERRIDE_DISAGREEMENT → ревью.
В духе VERIFY_BEFORE_TRUST: спорное не принимается молча.
[ПРИНЯТО; формулировки уточняются при реализации правил.]

**D6 — ОБЯЗАТЕЛЬНАЯ ГИГИЕНА ФОРМЫ:**
  - unicode_version в карточке ОБЯЗАТЕЛЬНА (NFKC/skeleton меняются
    между версиями; совместимо с уже готовым version pinning
    sources/17.0.0);
  - skeleton НЕ хранить как «канонический текст» (UTS#39: skeleton
    только для внутреннего сравнения);
  - canonical_target как ПОСЛЕДОВАТЕЛЬНОСТЬ, не один codepoint
    (NFKC даёт ﬁ→f+i; связано с офсет-развилкой норм-слоя).

**D7 — ВАЛИДАТОР/ЛИНТЕР карточек сообщества — ЗАРЕГИСТРИРОВАТЬ,
не делать сейчас.** Будущее расширение существующего MSL/MIP Linter
(не новая сущность): при PR запускать норм-слой, требовать
verification_snapshot или override_justification. Часть будущей
библиотеки-стандарта.

## ПРИНЦИП

Знак — включая гомоглиф (похожий знак: ／ вместо /, кириллица вместо

3. конвейер,

## ЧТО ЭТО РЕШАЕТ (раскол ревьюеров по норм-слою)

Прогон NORMALIZATION_LAYER_DESIGN дал раскол:
- ЛАГЕРЬ 1: `if ch in cards OR NFKC(ch) in cards` прямо в scan_signs —
  гомоглиф добавляется в validated_offsets кодом, на лету.
  → ОТКЛОНЁН. Нарушает дисциплину: впускает НЕВЕРИФИЦИРОВАННЫЙ
    знак в ядро (validated_offsets) в обход карточки и конвейера.

- ЛАГЕРЬ 2: отдельная структура confusable_flags, не в
  validated_offsets → дисциплину не нарушает, но sequence не видит
  комбинации из гомоглифов (обесценивает sequence-слой, который
  СОЗДАН читать комбинации — подтверждено докстрингом
  sequence_engine.py: «ловить межкарточные идиомы ../, ://»).
- РЕШЕНИЕ АВТОРА (третий путь, которого не было у ревьюеров):
  гомоглиф проходит ТЕМ ЖЕ путём, что любой знак — карточка +
  верификация + конвейер. Тогда он ЗАКОННО попадает в sequence
  (потому что стал верифицированным знаком), и дисциплина цела.

## РОЛЬ НОРМ-СЛОЯ (следствие)

Норм-слой в рантайме НЕ создаёт знаки. Он только ЧИТАЕТ то, что уже
верифицировано и лежит в карточках. Гомоглиф становится знаком
ЕДИНСТВЕННЫМ легальным способом — через карточку.

Аналогия автора: карточки знаков — будущая БИБЛИОТЕКА-справочник
(по типу SQL-базы). Норм-слой = ПОТРЕБИТЕЛЬ библиотеки (запрос «чей
это гомоглиф»), не генератор знаков на лету. Наполнение библиотеки —
через шаблоны и конвейер (в перспективе — силами сообщества по
стандарту автора), не хардкодом.

## ЧТО СОЗНАТЕЛЬНО НЕ РЕШЕНО ЗДЕСЬ (производное, на потом)

Эти вопросы — механика, решается позже, НЕ ломая принцип выше:
- гомоглиф = отдельный ТИП карточки или ПОЛЕ в карточке знака;
- «тонкая» карточка гомоглифа (наследует риск канонического знака +
  добавляет только верификацию), чтобы конвейер по ней был быстрым;
- механика офсетов при попадании гомоглифа в sequence
  (NFKC-expansion ﬁ→fi и пр. — как в CONVEYOR_PACKET_NORMALIZATION);
- дизайн поля гомоглифа в стандартном шаблоне карточки.

## ЗАФИКСИРОВАННОЕ ЕДИНОГЛАСНО РЕВЬЮ (6/6, остаётся в силе)

- FLAG_ONLY: слой флагирует, не меняет текст (анализатор ≠ санитайзер).

## РЕШЕНИЕ

Обработка гомоглифов и нормализация (NFKC + skeleton UTS#39 по
confusables.txt) выделяется в **ОТДЕЛЬНЫЙ СЛОЙ** системы, а НЕ
остаётся свойством отдельных карточек знаков.

## ОБОСНОВАНИЕ (market-critical, не косметика)

Текущая модель: каждая карточка знака несёт собственный список
`confusables` (поля `confusable_id`, `confusables` есть в
core/sign_core_card.py и core/load_card.py; заполняются вручную).

Проблема масштабирования: при азбуке на N знаков модель «confusables
в карточках» даёт КВАДРАТИЧНЫЙ рост сложности — до N×N пар гомоглифов,
которые ведутся вручную и устаревают с каждым релизом Unicode.
- 10 знаков — терпимо.
- 1000 знаков — до ~10^6 пар вручную = НЕПОДДЕРЖИВАЕМО.

Вывод автора (2026-07-07): «если в перспективе азбука будет состоять
из тысяч знаков, confusables в карточках выбьет её с рынка».
Конкурент с автоматической нормализацией обновляется одной кнопкой;
ручные confusables — тысячей правок.

Отдельный слой даёт:
- ЛИНЕЙНУЮ сложность: N знаков, ОДИН слой нормализации.
- Автообновляемость через уже готовый tools/unicode_sources_update.py
  (confusables.txt уже залит в sources/17.0.0/, поля в карточках
  уже существуют — инфраструктура наполовину готова).
- Новый знак защищён от гомоглифов автоматически (нормализация ДО
  того, как знак ищется), без ручного ведения пар.

## ЧТО ЭТО РЕШЕНИЕ ЕЩЁ НЕ РЕШАЕТ (вынесено в конвейер)

Признание слоя нужным ≠ готовая архитектура. Открытые проектные
вопросы, идущие через отдельный design-конвейер:
1. **Офсеты (КРИТИЧНО):** вся система построена на позициях символов
   (text.find, sign_offset_start/end, validated_offsets, text[offset]).
   NFKC МЕНЯЕТ длину текста → наивная нормализация сдвинет все офсеты
   и разорвёт связь single-sign ↔ sequence. Как совместить нормализацию
   с офсетной моделью — главный вопрос.
2. **Судьба старого поля confusables в карточках:** мигрировать в слой /
   оставить как override / удалить?
3. **Точка вклинивания слоя:** до scan_signs? отдельный проход? как не
   сломать sequence-матчинг (_find_literal_matches)?
4. **flag vs transform:** слой ПРИВОДИТ текст к канону (меняет) или
   только ФЛАГИРУЕТ (как invisible-guard, не strip)? — согласовать с
   принятой дисциплиной flag-only.

## СВЯЗЬ С ДРУГИМИ РЕШЕНИЯМИ

Этот слой — общий корень, в который упёрлись ОБА scope-конвейера:
- невидимые знаки → сюда выносятся гомоглифы/bidi;
- цифры → сюда выносятся Nd вне ASCII (٠١, ０１ fullwidth).
Решения D1 (невидимые=OPTION_2) и D8 (цифры ASCII-only + Nd в этот
слой) ОПИРАЮТСЯ на существование этого слоя. Поэтому оно принимается
ПЕРВЫМ.

════════════════════════════════════════════════════════════════
ЧАСТЬ 1 — КАРТОЧКИ-ЗАРОДЫШИ (EMBRYO CARDS)
════════════════════════════════════════════════════════════════

ПРОБЛЕМА, КОТОРУЮ ЗАКРЫВАЕТ:
Сейчас знак либо имеет полную карточку, либо проходит как неизвестный.
«Неизвестный» ловит отдельный механизм (регистратор) — только для
невидимок, отдельной сущностью. Это две параллельные системы
(карточки + регистратор) и дыра для всего, что вне регистратора.

РЕШЕНИЕ: знак ВСЕГДА представлен карточкой. Вопрос не «карточка или
дыра», а ЗРЕЛОСТЬ карточки. Добавляется нулевая ступень — ЗАРОДЫШ.

ЛЕСТНИЦА СТАТУСОВ (EMBRYO — новая нулевая ступень):
  EMBRYO             ← знак + юникод, БЕЗ суждения о риске
    → WORKING_DRAFT      (начали разбирать)
      → WORKINGLY_CLOSED
        → ARTIFACT_CONFIRMED

ЧТО В ЗАРОДЫШЕ (минимум, строго):
  CARD_STATUS: EMBRYO
  CODEPOINT: U+XXXX            ← ЛИЦО под гримом (ядро, обязательно)
  UNICODE_NAME: ...            ← из UnicodeData.txt
  SCRIPT: ...                  ← из Scripts.txt (когда подключим)
  GENERAL_CATEGORY: ...        ← грубый класс
  FIRST_SEEN: <контекст>       ← где система встретила (= заявка на разбор)
  VERDICT_CAPABILITY: NONE     ← КЛЮЧЕВОЕ: зародыш НЕ судит о риске

ПОЧЕМУ VERDICT_CAPABILITY: NONE — ГЛАВНОЕ:
Зародыш свидетельствует ПРИСУТСТВИЕ (вот знак, вот его код), НЕ выносит
ОПАСНОСТЬ. Иначе он превратится в антивирус, «на всякий случай»
подозревающий незнакомое. Зародыш только СМЫВАЕТ ГРИМ — показывает лицо.
Это UNVERIFIABLE как СТАТУС КАРТОЧКИ (не только как вердикт): честное
«вижу, не разобрал».

ЧТО ЭТО ДАЁТ:
  - убирает дыру «незнакомый знак проходит молча» (он теперь зародыш,
    светит лицом);
  - убирает антивирусный соблазн (зародыш не судит);
  - кормит экосистему: зародыши = ОЧЕРЕДЬ НА РАЗБОР. Система сама
    показывает, каких карточек не хватает (стратегия сообщества);
  - чистит архитектуру: одна лестница вместо «карточки + регистратор».
    РЕГИСТРАТОР становится ФАБРИКОЙ ЗАРОДЫШЕЙ (встретил незнакомый знак →
    завёл зародыш автоматически).

ГРАНИЦА (не переоценить):
  Зародыш НЕ защищает и НЕ заменяет полную карточку. Он мостик между
  «ничего» и «досье». Полный разбор (напр. гомоглиф через правило
  mixed-script) — на ступенях выше. Зародыш — честное «до разбора».

════════════════════════════════════════════════════════════════
ЧАСТЬ 2 — SCRIPT_ANOMALY_HIGHLIGHT (контекстное свечение)
════════════════════════════════════════════════════════════════

ФАБУЛА (авторская): свечение юникодом — НЕ всегда и НЕ для всех знаков.
Свечёт только знак, ЧУЖОЙ для своего окружения.
  - латинский текст → латиница молчит, кириллица СИЯЕТ;
  - кириллический текст → кириллица молчит, латиница СИЯЕТ;
  - чужак подсвечивается ОТНОСИТЕЛЬНО большинства, не абсолютно.

ПОЧЕМУ ЭТО КРИТИЧНО (без правила идея мертва):
Если светит ВСЁ — paypal.com → p(0070)a(0061)y(0079)... — нечитаемая
каша, человек тонет в кодах и перестаёт смотреть. Свечение всего = шум
= смерть оповещения (тот же flood, что боялись на witness пробелов).
Правило убирает шум: сияет ТОЛЬКО аномалия.
  pаypаl → всё серое, кроме двух «а», которые ГОРЯТ. Глаз летит на них.
Тихо, пока не чужак; ярко — на чужаке. Это и есть оповещение.

МЕХАНИКА:
  1. Взять токен/строку.
  2. Посчитать скрипты букв (Latin / Cyrillic / Greek / ...).
  3. Определить ДОМИНАНТУ («свой» скрипт) — по большинству И по КОНТЕКСТУ.
  4. Подсветить знаки, чей SCRIPT ≠ доминанта.

  Пример: pаypаl → 4 Latin (p,y,p,l) + 2 Cyrillic (а,а) → доминанта
  Latin → кириллица СИЯЕТ.

ЛОВУШКА 1 — 50/50 (аaаa, ара):
  Арифметика большинства не работает. Решение (та же логика): доминанту
  задаёт КОНТЕКСТ ОКРУЖЕНИЯ, не только счёт. Домен с .com (латинский TLD)
  → ожидается латиница → кириллица чужая, даже если её половина.
  Контекст задаёт «свой скрипт».

ЛОВУШКА 2 — ЛЕГИТИМНОЕ СМЕШЕНИЕ (купил iPhone; бренды, термины):
  Есть тексты, где два скрипта ЗАКОННЫ. Русский текст с англ. словом:
  «купил iPhone» — латинское iPhone НЕ чужак.
  РЕШЕНИЕ = рамка ОПОВЕЩЕНИЯ: система НЕ решает, законно смешение или
  атака. Она ПОДСВЕЧИВАЕТ и показывает человеку: «тут латиница в
  кириллическом тексте». Человек видит iPhone → «бренд, ок». Видит
  pаypаl → «подмена». РЕШАЕТ ОН.
  Антивирус тут ломается (надо решить: атака или бренд?). Оповещение —
  нет: показал, человек разобрался.

ФОРМУЛИРОВКА ПРАВИЛА:
  SCRIPT_ANOMALY_HIGHLIGHT: определить доминирующий скрипт строки/токена
  (по большинству букв + контексту: TLD, язык окружения). Подсветить
  («зажечь юникодом») ТОЛЬКО знаки, чей скрипт ОТКЛОНЯЕТСЯ от доминанты.
  Свои буквы молчат — чужак сияет. Система НЕ судит «атака ли это» —
  показывает аномалию, решает человек.

════════════════════════════════════════════════════════════════
СВЯЗЬ И СЛЕДСТВИЯ
════════════════════════════════════════════════════════════════

- ЕДИНЫЙ ПРИНЦИП КОНТЕКСТНОСТИ: аномалия ОТНОСИТЕЛЬНО контекста, не
  абсолютно. ZWSP опасен в домене / безопасен в тайском. Кириллица
  сияет в латинском / молчит в русском. Одно правило везде.

- СВЕЧЕНИЕ = ЧИСТОЕ ОПОВЕЩЕНИЕ: оно ничего не решает, делает ВИДИМЫМ.
  Подсвечивает ВОПРОС, не даёт ОТВЕТ. Метрика системы — не «сколько
  поймала» (антивирус), а «насколько ясно показала» (оповещение).

- ЗАВИСИМОСТЬ ОТ Scripts.txt: чтобы понять «латинская буква в кириллице»,
  нужен SCRIPT каждой буквы. Scripts.txt / ScriptExtensions.txt — НЕТ в
  источниках проекта. Свечение НЕВОЗМОЖНО без них. Ещё один довод
  подключить первыми в UCD-ревизии. (unicodedata частично умеет, но
  полный версионированный ответ — в Scripts.txt.)

- ГОМОГЛИФЫ через это правило = НЕ тысяча карточек на каждую букву, а
  ОДНО правило свечения + одна образцовая гомоглиф-карточка-эталон.
  Не строить сверху.

- ЗАРОДЫШ + СВЕЧЕНИЕ вместе: каждый зародыш несёт SCRIPT → mixed-script
  аномалия видна ДАЖЕ на зародышах, до полных карточек.

ЧАСТЬ 3 — VARIANT_DISCLOSURE (раскрытие вариантов)
════════════════════════════════════════════════════════════════

ОБРАЗ (авторский): сонар не различает карася и окуня — он видит, что
ЕСТЬ рыба, её размер, глубину. Вид определяет рыбак.
Развитие: система может пойти на шаг дальше голого сонара — сказать
«тут рыба; по эху похоже на карася, окуня или леща — смотри сам».
НЕ выбирает вид (это классификатор/антивирус, гадание о намерении),
а РАСКРЫВАЕТ возможные прочтения и отдаёт выбор человеку.

ТРИ УРОВНЯ ОПОВЕЩЕНИЯ (триада, ни один не решает за человека):
  1. СОНАР            — есть аномалия («тут рыба»)
  2. СВЕЧЕНИЕ         — вот она, подсвечена (SCRIPT_ANOMALY_HIGHLIGHT)
  3. VARIANT_DISCLOSURE — вот как её можно прочесть, суди

ГРАНЬ (критическая):
  «Тут фишинг»                    → антивирус, гадание о намерении. ❌
  «Тут кириллица в латинском домене; бывает при: фишинге / легитимном
   адресе / опечатке раскладки»    → оповещение с раскрытием. ✅
  Первое ЗАКРЫВАЕТ вопрос за человека. Второе РАСКРЫВАЕТ вопрос ДЛЯ
  человека. Проект — за второе.

ПРИМЕР (gоogle.com, кириллическая о U+043E):
  ⚠ Домен содержит знак, чужой для латинского окружения:
     поз.2: о — U+043E (Cyrillic), выглядит как латинское o (U+006F)
     Возможные прочтения:
     • ГОМОГЛИФ-подмена бренда (кириллица маскирует латиницу) — частый фишинг
     • легитимный не-латинский домен (если адрес осмысленно кириллический)
     • случайная опечатка раскладки
     Решение за тобой.
  Человек видит ФАКТЫ (знак, код, скрипт) + ВАРИАНТЫ → решает мгновенно.

ИСТОЧНИК ВАРИАНТОВ — КАРТОЧКА, НЕ ВЫДУМКА:
  Карточка уже содержит прочтения: SAFE_CASE (где легально), RISK_CASE
  (где опасно), AMBIGUOUS. Система НЕ изобретает версии на ходу
  (галлюцинация), а ПРЕДЪЯВЛЯЕТ содержимое досье. Оповещение =
  РАЗВЕРНУТЬ досье, а не свернуть в приговор.
  Нет карточки → зародыш → «знак чужой, код такой-то, прочтения ПОКА
  НЕ РАЗОБРАНЫ» — честно, без выдуманных вариантов.

ПРАВИЛО:
  VARIANT_DISCLOSURE: при обнаруженной аномалии система НЕ выносит
  вид/вердикт, а РАСКРЫВАЕТ известные прочтения знака в данном контексте
  (из карточки: safe/risk/ambiguous) как ГИПОТЕЗЫ, не как решение.
  «Возможно A, B или C — суди сам.» Только для ПОДСВЕЧЕННЫХ аномалий,
  только РЕЛЕВАНТНЫЕ контексту, только из ПРОВЕРЕННОГО досье. НЕ
  ранжировать уверенно (уверенный процент = скатывание в суждение о
  намерении = антивирус).

ГРАНИЦА ПРОТИВ FLOOD (из SCRIPT_ANOMALY_HIGHLIGHT):
  Варианты — ТОЛЬКО для подсвеченных аномалий. Норма молчит: обычная
  латинская o в латинском домене → ноль вариантов, тишина. 8 гипотез на
  каждый знак = flood = смерть оповещения. Аномалия → развернуть версии;
  норма → молчать.

СВЯЗЬ:
  - завершает триаду сонар→свечение→раскрытие, всё в рамке оповещения;
  - не требует нового механизма: система ПОКАЗЫВАЕТ safe/risk/ambiguous
    карточки, а не сворачивает в один вердикт;
  - метрика та же: не «сколько поймала», а «насколько ясно раскрыла».

2. ГЛАВНЫЙ ФАКТ, ДОКАЗАННЫЙ ЗАПУСКОМ (проба шаблона на ZWSP)

МЕХАНИЗМ ДЕТЕКТОРА КАНОН-АГНОСТИЧЕН. МЕТАДАННЫЕ ОТНОШЕНИЯ — НЕТ.

`_demask` вычищает всё, что попало в `run_mask_chars`. Но `run_mask_chars`
набирается из SIGN_RELATIONS-кандидатов, а блок ребра ТРЕБУЕТ TARGET +
RELATION_TYPE из набора мимикрии {CONFUSABLE_OF, NFKC_MAPS_TO,
VISUAL_MIMIC_OF}. У ZWSP канона нет.

Три прогона одного входа (gоog<ZWSP>／le.com — известная открытая дыра):

  A — честно (нет ребра, канона нет):
      ZWSP роняется MATCHER_NOT_FOUND → FREE_TEXT → ДЫРА ОТКРЫТА.

  B — честный тип (выдуманный BOUNDARY_DISRUPTOR, TARGET=NONE):
      загрузчик пишет UNKNOWN_RELATION_TYPE warning, ребро активно →
      HOST/HIGH → ДЫРА ЗАКРЫТА ЦЕНОЙ ПРЕДУПРЕЖДЕНИЯ.

  C — валидный тип (VISUAL_MIMIC_OF, TARGET=U+0020, семантически ЛОЖНЫЙ):
      грузится без единого warning → HOST/HIGH → ДЫРА ЗАКРЫТА ЦЕНОЙ ЛЖИ
      (ZWSP НЕ мимикрирует пробел).

ВЫВОД: шаблон вынуждает выбор между ПРЕДУПРЕЖДЕНИЕМ и ЛОЖЬЮ. Честного
типа отношения для знака-разрушителя в оси не существует.

Природа ZWSP на этом входе — НЕ мимикрия под ZWJ и НЕ под пустоту, а
BOUNDARY_DISRUPTOR: он рвёт границу точного совпадения. Механизм риска —
диверсия, не подделка. Это отдельное семейство, которое конвейер в теории
поставил почти хвостом (адверсариальный: BOUNDARY_STATE_MISMATCH, тип 9),
а проба подтвердила как ПЕРВИЧНЫЙ для реального входа.

Природа канона у невидимых тройственна (теория + практика сошлись):

  (а) невидимый → невидимый ПО КЛАССУ ФИЛЬТРА (не по Unicode-функции!).

      Тип: CLASSIFIER_COLLISION_WITH.

  (б) невидимый → ПУСТОТА. Канон не кодпоинт. КРИТИЧНО: выражать явным

  (в) невидимый → РАЗРЫВ ГРАНИЦЫ. Не мимикрия вообще, а диверсия точного

      Тип: BOUNDARY_DISRUPTOR / BOUNDARY_STATE_MISMATCH.

Отдельно:

    Stateful, нужны SPAN_START/END/TERMINATOR. Почти консенсус: отдельное

    (вариант R3, гибрид).
  VS16 (U+FE0F) — НЕ мимикрия, а MODIFIES_VISIBLE_HOST (меняет представление
    соседа). Требует preceding valid base.

ВАЖНО (адверсариальный, VERIFIED): DEFAULT_IGNORABLE ≠ ПУСТО ≠ SAFE_TO_DELETE.
  ZWSP разрешает разрыв, WJ ЗАПРЕЩАЕТ, ZWNJ подавляет соединение — они
  ПРОТИВОПОЛОЖНЫ по функции, но все невидимы и все Default_Ignorable.
  Следствие для детектора: `_demask` НЕ должен слепо удалять все невидимые —
  удаление ZWNJ исказит смысл (персидская орфография), а не очистит.

════════════════════════════════════════════════════════════════

        ЗНАКИ — ЭТО ГРИМ НА ЮНИКОДЕ.

Юникод — лицо. Знак (форма на экране) — грим поверх лица.
Под одинаковым гримом могут быть РАЗНЫЕ лица.

  а  — грим
  ├─ лицо U+0061 (Latin a)
  └─ лицо U+0430 (Cyrillic а)

Один грим, два лица. Глаз видит грим. Обман живёт в гриме.

════════════════════════════════════════════════════════════════
МИМИКРИЯ = ЧУЖОЕ ЛИЦО В ЗНАКОМОМ ГРИМЕ
════════════════════════════════════════════════════════════════

Мимикрия — это когда чужое лицо надевает знакомый грим, чтобы
выдать себя за своего.

  paypal.com  — все лица латинские (свои)
  pаypаl.com  — лицо U+0430 (кириллица) в латинском гриме «a»
                чужак под знакомым гримом → подделка бренда

Ключевое: грим сам по себе не виновен. Лицо U+0430 ЗАКОННО в русском
слове (банан). Оно становится мимикрией ТОЛЬКО в чужом контексте —
когда чужое лицо влезает в латинское окружение под латинским гримом.
Мимикрия контекстна, как всё в системе.

════════════════════════════════════════════════════════════════
ТРИ КЛАССА АТАК = ТРИ СПОСОБА ОБМАНУТЬ ЧЕРЕЗ ГРИМ
════════════════════════════════════════════════════════════════

ОДНА метафора объясняет все три класса, над которыми работает проект:

1. ГОМОГЛИФ — чужое лицо в знакомом гриме.
   U+0430 (кириллица) в гриме «a». Смыть грим → чужак голый.
   Коды НЕ спутываемы: U+0430 и U+0061 — очевидно разные числа.
   Мимикрия умирает в слое кода.

2. МАСКА (／ U+FF0F) — лицо, которое под смывкой СТАНОВИТСЯ другим.
   Грим сложный: NFKC-смывка превращает U+FF0F → U+002F.
   Смыл грим — под ним оригинал, которым знак и притворялся.
   Здесь свечения мало — нужен контекст (декомпозиция + место).

3. НЕВИДИМКА (ZWSP U+200B) — ГРИМ БЕЗ ЛИЦА.
   Визуального лица нет вовсе, один грим-пустышка.
   Опасен тем, что грима не видно совсем.
   Здесь свечение необходимо, но недостаточно — риск решает контекст.

Три атаки — три способа обмануть через грим.
Защита ОДНА: не верить гриму, читать лицо (код).

════════════════════════════════════════════════════════════════
СВЕЧЕНИЕ ЮНИКОДОМ = СМЫТЬ ГРИМ
════════════════════════════════════════════════════════════════

Мимикрия живёт ТОЛЬКО в слое формы (грима). Подними знак в слой кода
(лица) — мимикрия УМИРАЕТ, потому что коды уникальны и не спутываемы.

  Режим «форма» (что видит человек):
    g о o g l e      — всё одинаково, обман работает

  Режим «свечение» (лица под гримом):
    0067 0430 006F 0067 006C 0065
         ↑ 0430 среди 006x — чужак голый, торчит из ряда

Не «детектор ИЩЕТ обман» (гадание, вероятность) — а СМЕНА СЛОЯ, где
обману негде спрятаться (факт). Это тот же якорь против галлюцинаций,
приложенный к восприятию: ФОРМА ГАЛЛЮЦИНИРУЕТ, КОД — НЕТ.

Свечение скриптом (Scripts.txt) усиливает: знак светится не только
кодом, но и происхождением лица (Latin/Cyrillic/Greek) — тогда чужак
виден даже без запоминания кодов: «в одном слове два скрипта».

ГРАНИЦА (не переоценить):
  - гомоглиф — свечение убивает НАПОВАЛ (весь обман в гриме);
  - маска/невидимка — свечение НЕОБХОДИМЫЙ ПЕРВЫЙ СЛОЙ, но не полный
    (нужен контекст: NFKC для маски, позиция для невидимки).

════════════════════════════════════════════════════════════════
АРХИТЕКТУРА, ВЫВЕДЕННАЯ ИЗ МЕТАФОРЫ
════════════════════════════════════════════════════════════════

Система работает НЕ со знаками — с ЛИЦАМИ ПОД ГРИМОМ.

  ДЕТЕКТОР      — не «читает текст» (видит грим), а читает КОДЫ
                  (видит лица). Весь патч-цикл дня (P0, F-NEW-2,
                  host-span) — борьба с тем, что система местами
                  ВЕЛАСЬ НА ГРИМ (реконструировала форму) вместо
                  чтения лиц.

  КАРТОЧКА      — досье на ЛИЦО: настоящий код; под каким гримом
                  ходит легально (кириллица в русском); где грим —
                  обман (кириллица в латинском домене).

  РЕГИСТРАТОР   — ловит НЕЗНАКОМЫЙ ГРИМ: «вижу грим, лица в досье
                  нет — придержи, посмотри» (UNVERIFIABLE, witness).

  СВЕЧЕНИЕ      — смывка грима ДЛЯ ЧЕЛОВЕКА: показать лица, пусть
                  сам увидит чужака. Рамка оповещения: система светит,
                  человек судит.

════════════════════════════════════════════════════════════════
СВЯЗЬ С ПРИНЦИПАМИ ПРОЕКТА
════════════════════════════════════════════════════════════════

- ФОРМА ГАЛЛЮЦИНИРУЕТ, КОД — НЕТ — частный случай общего:

# ARCH_DECISION: HOMOGLYPH ENTERS ONLY VIA A CARD (discipline)

**Status:** AUTHOR_DECISION (accepted)
**Date:** 2026-07-07
**Decision author:** Ruslan Malyavsky (AUTHOR_DECISION_STATUS_AUTHORITY)

## PRINCIPLE

A sign — including a homoglyph (a look-alike sign: ／ instead of /,
Cyrillic instead of Latin, fullwidth, etc.) — has NO right to appear in
a module next to a genuine sign while bypassing:
1. a sign card,
2. Unicode verification (NFKC / UTS#39 skeleton),
3. the conveyor,
4. AUTHOR_DECISION.

**No signs "on the fly." No back door into validated_offsets via code.**

## WHAT THIS RESOLVES (the reviewers' split on the norm layer)

The NORMALIZATION_LAYER_DESIGN run produced a split:
- CAMP 1: `if ch in cards OR NFKC(ch) in cards` right in scan_signs —
  the homoglyph is added to validated_offsets by code, on the fly.
  → REJECTED. Violates discipline: admits an UNVERIFIED sign into the
    core (validated_offsets) bypassing the card and the conveyor. This
    is exactly the FALSE_TRUST the whole project stands against.
- CAMP 2: a separate confusable_flags structure, not in
  validated_offsets → does not violate discipline, but sequence never

- AUTHOR'S DECISION (a third path, absent from the reviewers): the
  homoglyph travels the SAME path as any sign — card + verification +
  conveyor. Then it LEGALLY reaches sequence (because it has become a

## ROLE OF THE NORM LAYER (consequence)

The norm layer at runtime does NOT create signs. It only READS what has
already been verified and stored in cards. A homoglyph becomes a sign
by the ONLY legal means — through a card.

Author's analogy: sign cards are a future LIBRARY/reference (SQL-database
style). The norm layer = a CONSUMER of the library (query "whose
homoglyph is this"), not an on-the-fly sign generator. Populating the
library happens through templates and the conveyor (in perspective — by
the community following the author's standard), not via hardcode.

# ARCH_DECISION: NORMALIZATION/CONFUSABLES — SEPARATE LAYER

**Status:** AUTHOR_DECISION (accepted)
**Date:** 2026-07-07
**Decision author:** Ruslan Malyavsky (AUTHOR_DECISION_STATUS_AUTHORITY)
**Type:** project-level architecture decision

---

## DECISION

Homoglyph handling and normalization (NFKC + skeleton UTS#39 over
confusables.txt) is extracted into a **SEPARATE LAYER** of the system,
NOT kept as a property of individual sign cards.

## RATIONALE (market-critical, not cosmetic)

Current model: each sign card carries its own `confusables` list
(fields `confusable_id`, `confusables` exist in core/sign_core_card.py
and core/load_card.py; filled manually).

Scaling problem: with an alphabet of N signs, the "confusables in
cards" model gives QUADRATIC complexity growth — up to N×N homoglyph
pairs maintained by hand, going stale with each Unicode release.
- 10 signs — tolerable.
- 1000 signs — up to ~10^6 pairs by hand = UNMAINTAINABLE.

Author's conclusion (2026-07-07): "if the alphabet eventually consists
of thousands of signs, confusables-in-cards will knock it out of the
market." A competitor with automatic normalization updates with one
button; manual confusables mean a thousand edits.

A separate layer gives:
- LINEAR complexity: N signs, ONE normalization layer.
- Auto-updatability via the already-built
  tools/unicode_sources_update.py (confusables.txt is already committed
  to sources/17.0.0/, card fields already exist — infrastructure is
  half-ready).
- A new sign is protected from homoglyphs automatically (normalization
  BEFORE the sign is searched), without hand-maintaining pairs.

## WHAT THIS DECISION DOES NOT YET RESOLVE (sent to conveyor)

Recognizing the layer as needed ≠ finished architecture. Open design
questions, going through a separate design conveyor:
1. **Offsets (CRITICAL):** the whole system is built on character
   positions (text.find, sign_offset_start/end, validated_offsets,
   text[offset]). NFKC CHANGES text length → naive normalization will
   shift all offsets and break the single-sign ↔ sequence link. How to
   reconcile normalization with the offset model is the main question.
2. **Fate of the old confusables field in cards:** migrate to layer /
   keep as override / delete?
3. **Layer insertion point:** before scan_signs? separate pass? how not
   to break sequence matching (_find_literal_matches)?
4. **flag vs transform:** does the layer CANONICALIZE text (mutate) or
   only FLAG (like invisible-guard, not strip)? — align with the
   accepted flag-only discipline.

## RELATION TO OTHER DECISIONS

This layer is the common root that BOTH scope conveyors hit:
- invisible signs → homoglyphs/bidi go here;
- digits → non-ASCII Nd (٠١, ０１ fullwidth) go here.
Decisions D1 (invisible=OPTION_2) and D8 (digits ASCII-only + Nd into
this layer) DEPEND on this layer existing. Hence it is decided FIRST.

via www.unicode.org):

- UnicodeData.txt (sha 2e1efc1dcb59c575)
- confusables.txt (sha 091c7f82fc39ef20)

  Reason: MSL/MIP's main threat is exactly STRUCTURAL attacks on

and cleanliness now. This is your product call, not an architecture detail.

`_demask` вычищает всё, что попало в `run_mask_chars`. Но `run_mask_chars`

RELATION_TYPE из набора мимикрии {CONFUSABLE_OF, NFKC_MAPS_TO,

Три прогона одного входа (gоog<ZWSP>／le.com — известная открытая дыра):

  A — честно (нет ребра, канона нет):
      ZWSP роняется MATCHER_NOT_FOUND → FREE_TEXT → ДЫРА ОТКРЫТА.

  B — честный тип (выдуманный BOUNDARY_DISRUPTOR, TARGET=NONE):

      HOST/HIGH → ДЫРА ЗАКРЫТА ЦЕНОЙ ПРЕДУПРЕЖДЕНИЯ.

  C — валидный тип (VISUAL_MIMIC_OF, TARGET=U+0020, семантически ЛОЖНЫЙ):
      грузится без единого warning → HOST/HIGH → ДЫРА ЗАКРЫТА ЦЕНОЙ ЛЖИ
      (ZWSP НЕ мимикрирует пробел).

ВЫВОД: шаблон вынуждает выбор между ПРЕДУПРЕЖДЕНИЕМ и ЛОЖЬЮ. Честного
типа отношения для знака-разрушителя в оси не существует.

Природа ZWSP на этом входе — НЕ мимикрия под ZWJ и НЕ под пустоту, а
BOUNDARY_DISRUPTOR: он рвёт границу точного совпадения. Механизм риска —
диверсия, не подделка. Это отдельное семейство, которое конвейер в теории
поставил почти хвостом (адверсариальный: BOUNDARY_STATE_MISMATCH, тип 9),

Природа канона у невидимых тройственна (теория + практика сошлись):

  (а) невидимый → невидимый ПО КЛАССУ ФИЛЬТРА (не по Unicode-функции!).
