КАК ПОЛЬЗОВАТЬСЯ ЭТИМ ШАБЛОНОМ
============================================================

Это ФОРМА для создания конвейерного пакета — документа, который
отправляется внешним моделям-ревьюерам для организации одного
раунда проверки. Подходит для трёх типов раундов, обнаруженных
в практике проекта:

  ТИП_1: REVIEW — ревью текстового документа (правила, шаблон,
    спецификация) против критериев качества/трассируемости
  ТИП_2: SIMULATION — сквозное исполнение pipeline (карточка
    знака → MODULE_TEMPLATE → INTEGRATOR_TEMPLATE → результат)
  ТИП_3: AUDIT — сравнительная проверка нескольких артефактов
    друг против друга (например, структурная сверка карточек)

Выбери подходящий тип в начале заполнения — это определит, какие
блоки из B.1–B.9 (раздел ЗАДАНИЕ) тебе нужны, а какие можно
удалить как нерелевантные.

Каждое поле в угловых скобках <...> заполняется конкретикой
текущего раунда.

  выводов на основе более ранних сообщений о других задачах.

RULE_REMINDER: VERIFY_BEFORE_TRUST_MANDATORY
  Если ты ссылаешься на содержимое других документов проекта
  (карточки знаков, правила, шаблоны) в своём ревью — проверяй
  это напрямую по приложенным файлам, не по памяти и не по чужим
  пересказам. Формальный акт "уточнения" не делает второе
  утверждение автоматически более достоверным без независимой
  проверки против первоисточника.

RULE_REMINDER: DIFFERENTIATION_CHECK_MANDATORY
  Если один знак/элемент тестируется в N разных контекстах И
  результат идентичен во всех N контекстах ТО автоматически
  ARCHITECTURE_BUG — эта находка не может быть понижена по
  дискреции отдельного ревьюера. (Применять для раундов типа
  SIMULATION с несколькими тестовыми кейсами.)

RULE_REMINDER: AUTHOR_DECISION_STATUS_AUTHORITY
  Вердикт ревьюера ≠ финальный статус проекта. Любое заявление о
  WORKINGLY_CLOSED / ARTIFACT_CONFIRMED / READY_FOR_USE является
  рекомендацией, не фактом, до явного принятия через AUTHOR_DECISION
  координирующей стороны (автора проекта). Это правило применяется
  к КАЖДОМУ ревьюеру, включая того, кто формально является
  "MASTER-ORCHESTRATOR" или координатором сессии — такая роль не
  даёт полномочий присваивать финальный статус. Найдено по итогам

  раздела 0 по итогам внешнего ревью (GPT-5.5, Copilot).

RULE_REMINDER: PER_FINDING_STATUS_AND_BASIS_MANDATORY
  Для КАЖДОЙ находки любого ревьюера обязательны два поля:
    FINDING_STATUS: VERIFIED | REJECTED | UNVERIFIABLE
    FINDING_BASIS:  на чём основано — трейс по коду с ТОЧНЫМ входом и
                    ТОЧНОЙ строкой/веткой, ЛИБО прямая цитата из пакета
                    с локатором, ЛИБО честное «не смог проверить».
  Вердикт без BASIS НЕ ПРИНИМАЕТСЯ к арбитражу. Утверждение — не
  доказательство. UNVERIFIABLE — законный ответ; догадка, выданная за
  проверку, — нет. Голое «VERIFIED»/«проверил»/«очевидно» без
  METHOD+TARGET+OBSERVED = отсутствие FINDING_STATUS (декоративное поле).
  Полная механика (трёхзначность, BASIS_MINIMUM, запреты элизии
  UNVERIFIABLE→VERIFIED и гильотины UNVERIFIABLE→REJECTED,
  FINDING_STATUS≠ISSUE_SEVERITY, UNIVERSAL_SCOPE) — в Части C,
  FINDING_STATUS_RULE; здесь она поднята в раздел 0, чтобы действовать
  для ЛЮБОГО пакета с момента постановки задачи, а не только в формате
  поставки. Найдено по итогам круга 2026-07-12 (узкий круг по

  догадка выдана за проверку); ещё один голос второй раз подряд рецензировал

B.<N> КЛАССИФИКАЦИЯ НАХОДОК

  Для пакетов REVIEW/AUDIT:
    CRITICAL_ISSUE: документ содержит запрещённую конструкцию,
      или пропускает обязательное требование, без которого
      документ не может выполнять свою функцию
    MAJOR_ISSUE: формулировка неоднозначна настолько, что разные
      пользователи документа поймут/заполнят его принципиально
      по-разному
    MINOR_ISSUE: неточность, не создающая риск расхождения, но
      требующая уточнения
    TRACE_ONLY_NOTE: наблюдение, не требующее изменений

  Для пакетов SIMULATION:
    ARCHITECTURE_BUG: pipeline не может быть пройден даже при
      корректном входе; OUTPUT одного этапа не совпадает с INPUT
      следующего; обязательная проверка не может быть выполнена
    CARD_DATA_GAP: используемый артефакт (карточка) не содержит
      поле, требуемое pipeline
    TEMPLATE_TO_TEMPLATE_INTERFACE_GAP: downstream-шаблон
      (например, MODULE_TEMPLATE) ожидает поле или структуру,
      которую upstream-документ (карточка знака) формально не
      гарантирует — отличается от CARD_DATA_GAP тем, что это не
      пробел в одной конкретной карточке, а нескоординированность
      между двумя разными документами проекта. Найдено по опыту
      раунда SOLIDUS (отсутствие явного поля ZONE), добавлено по
      итогам внешнего ревью (GPT-5.5).
    PIPELINE_INTERFACE_GAP: более общий класс — OUTPUT одного
      этапа pipeline формально не совпадает с INPUT следующего
      этапа, даже если человек может восстановить смысл вручную.
      Отличается от TEMPLATE_TO_TEMPLATE_INTERFACE_GAP тем, что
      применяется не только к паре "карточка → MODULE_TEMPLATE",
      но и к любой паре этапов pipeline (например, OUTPUT
      MODULE_TEMPLATE vs INPUT INTEGRATOR_TEMPLATE). Добавлено по
      итогам повторного внешнего ревью (GPT-5.5).
    POLICY_GAP: демо-политика не покрывает нужный случай
    SIMULATION_INPUT_GAP: вход не содержит данных, не заявленных
      как часть симуляции
    TRACE_ONLY_NOTE: замечание, не блокирующее pipeline

  Каждая находка ревьюера несёт трёхзначный статус проверки:

    Валидное ОСНОВАНИЕ обязано называть:
      METHOD  — чем проверено (grep / diff / запуск / цитата / сверка)
      TARGET  — где (файл / секция / строка / поле)
      OBSERVED — что реально найдено
    EXPECTED и LOCATOR (номер строки / путь / команда / test id) —
    настоятельно рекомендуются; для VERIFIED и REJECTED LOCATOR или
    воспроизводимая команда обязательны, где это возможно. Для
    UNVERIFIABLE основание обязано объяснить, ПОЧЕМУ проверка не
    может быть завершена машинно.
  DECORATIVE_BASIS_GUARD:
    Голые «проверил» / «очевидно» / «просмотрел» без METHOD+TARGET+
    OBSERVED — НЕ основание. Такая находка = отсутствие FINDING_STATUS.
  FINDING_STATUS ≠ ISSUE_SEVERITY:
    Статус проверки (VERIFIED/REJECTED/UNVERIFIABLE) ортогонален
    серьёзности (CRITICAL/MAJOR/MINOR). Находка может быть VERIFIED
    и MINOR; или UNVERIFIABLE и критически важной (→ AUTHOR_DECISION).
  UNIVERSAL_SCOPE:
    FINDING_STATUS_RULE применяется к КАЖДОЙ находке во ВСЕХ форматах
    поставки (REVIEW_RESULT, AUDIT_RESULT, SIMULATION_RESULT), если
    пакет явно не объявил обратное.

Когда несколько ревьюеров возвращают результаты по одному пакету:

1. НЕ суммировать находки механически как "большинство право".
   Для каждого спорного пункта — лично проверять факт по
   первоисточнику (grep по файлу, не пересказ), прежде чем
   решать, кто прав.

2. Любое сообщение, заявляющее финальный статус документа
   ("WORKINGLY_CLOSED", "ARTIFACT_CONFIRMED" и т.д.) от лица
   модели-ревьюера — НЕ валидное действие. Финальный статус
   присваивается только через AUTHOR_DECISION координирующей
   стороны (автора проекта), не одностороннее заявление участника
   конвейера.

3. Находка, помеченная одним ревьюером как CRITICAL/MAJOR, не
   автоматически верна только потому, что она строже остальных.
   Проверять формулировку первоисточника (правил/спецификации) —
   действительно ли нарушено буквальное требование, или это
   предложение по улучшению, которое следует классифицировать
   как опциональное расширение, а не блокирующую находку.
