ARCHITECTURE_PRINCIPLES:
  PRINCIPLE_1: SEQUENCE_INTEGRATOR receives SEQUENCE_OUTPUT from SEQUENCE_MODULE
  PRINCIPLE_2: SEQUENCE_INTEGRATOR analyzes sequence-specifics, not only RISK_LEVEL
  PRINCIPLE_3: SEQUENCE_INTEGRATOR forms RUNTIME_ACTION_REQUEST (advisory), not FINAL_VERDICT
  PRINCIPLE_4: SEQUENCE_INTEGRATOR considers INTENSITY (number of identical signs)
  PRINCIPLE_5: SEQUENCE_INTEGRATOR considers COMBINATION (different signs together)
  PRINCIPLE_6: SEQUENCE_INTEGRATOR considers EPOCH_CONFLICT (different epochs in one sequence)
  PRINCIPLE_7: SEQUENCE_INTEGRATOR does not change INTERPRETATION of individual signs
  PRINCIPLE_8: SEQUENCE_INTEGRATOR is not runtime — only adapter
  PRINCIPLE_9: SEQUENCE_INTEGRATOR does not set policy — only applies SEQUENCE_INTEGRATOR_POLICY
  PRINCIPLE_10: SEQUENCE_INTEGRATOR does not cache results between sessions (SESSION_ONLY)
  PRINCIPLE_11: SEQUENCE_INTEGRATOR_TEMPLATE is a specialized profile of INTEGRATOR_TEMPLATE
  PRINCIPLE_12: SEQUENCE_INTEGRATOR_TEMPLATE inherits all limitations of INTEGRATOR_TEMPLATE
  PRINCIPLE_13: SEQUENCE_INTEGRATOR_TEMPLATE extends INTEGRATOR_TEMPLATE, does not replace it

INTEGRATION_CHAIN:
  INPUT: SEQUENCE_OUTPUT → SEQUENCE_INTEGRATOR_INSTANCE
  OUTPUT: RUNTIME_ACTION_REQUEST → RUNTIME
  BOUNDARY: SEQUENCE_INTEGRATOR ≠ SEQUENCE_MODULE (SEQUENCE_INTEGRATOR adapts, SEQUENCE_MODULE aggregates)
  BOUNDARY: SEQUENCE_INTEGRATOR ≠ INTEGRATOR (SEQUENCE_INTEGRATOR processes sequences, INTEGRATOR processes single signs)
  BOUNDARY: SEQUENCE_INTEGRATOR may work together with INTEGRATOR (if runtime requires both)

PROCESSING_PIPELINE:

PIPELINE_STAGES: 7 processing stages (STAGE_1–7)

STAGE_1: SEQUENCE_INPUT_VALIDATION
  INPUT: SEQUENCE_OUTPUT + SEQUENCE_INTEGRATOR_POLICY
  CHECK_0: SEQUENCE_INTEGRATOR_POLICY_VALIDATION (policy structure: INTENSITY_RULES, COMBINATION_RULES, EPOCH_CONFLICT_RULES must be present)
  CHECK_1: SEQUENCE_OUTPUT contains all mandatory fields
  CHECK_2: SEQUENCE_EFFECT_FIELDS_STATUS = VALID
  CHECK_3: SEQUENCE_INTEGRATOR_POLICY is loaded and compatible
  CHECK_4: SEQUENCE_LENGTH ≤ MAX_SEQUENCE_LENGTH (matches SEQUENCE_MODULE)
  CHECK_5: SEQUENCE_LENGTH ≥ 2 (protection against corrupted SEQUENCE_OUTPUT)
    IF SEQUENCE_LENGTH < 2 → ERROR_TYPE = SEQUENCE_OUTPUT_INVALID
  CHECK_6: POLICY_CONSISTENCY — SEQUENCE_POLICY.MAX_SEQUENCE_LENGTH = SEQUENCE_INTEGRATOR_POLICY.MAX_SEQUENCE_LENGTH
    IF mismatch → ERROR_TYPE = SEQUENCE_POLICY_INTEGRATOR_MISMATCH
  FAILURE: ERROR_TYPE = SEQUENCE_OUTPUT_INVALID or SEQUENCE_POLICY_INVALID

STAGE_2: INTENSITY_ANALYSIS
  INPUT: SOURCE_INTERPRETATION_LIST + SOURCE_SIGN_LIST + SEQUENCE_LENGTH
  ACTION: determining intensity by sub-sequences
  LOGIC:
    SUB_SEQUENCE_SCAN: searching repeated sub-sequences (N ≥ 2 identical signs in a row)
    INTENSITY_DETECTION:
      IF repeated same CODEPOINT or same SIGN_GROUP → INTENSITY_FLAG = YES
      INTENSITY_LEVEL per sub-sequence:
        LOW: 2 identical signs in a row
        MEDIUM: 3 identical signs in a row
        HIGH: 4-9 identical signs in a row
        CRITICAL: 10+ identical signs in a row (spam suspicion)
    GLOBAL_INTENSITY: MAX(INTENSITY_LEVEL of all sub-sequences)
    IF GLOBAL_INTENSITY ≥ HIGH → increase SEQUENCE_RISK_LEVEL by 1 level
    IF GLOBAL_INTENSITY = CRITICAL → SEQUENCE_RISK_LEVEL = CRITICAL (spam)
  EXAMPLE: 💀💀💀😭 = sub-sequence [💀💀💀] → INTENSITY HIGH
  EXAMPLE: 💀💀💀💀💀💀💀💀💀💀 = 10x → INTENSITY CRITICAL
  NOTE: INTENSITY_ANALYSIS does not create new semantics — only quantitative assessment
  FORMULA: SAME_INTERPRETATION ≠ SAME_SIGN_INTENSITY
  FORMULA: SUB_SEQUENCE_INTENSITY = STRUCTURAL_PROPERTY

STAGE_3: COMBINATION_ANALYSIS
  INPUT: SOURCE_INTERPRETATION_LIST + EPOCH_SEQUENCE_CONTEXT + SOURCE_SIGN_LIST
  ACTION: determining combination and idiom recognition
  IDIOM_RECOGNITION:
    SOURCE: IDIOM_REGISTRY (loaded from SEQUENCE_INTEGRATOR_POLICY.COMBINATION_RULES.KNOWN_IDIOMS)
    MECHANISM: exact match of CODEPOINT sequence or INTERPRETATION
    IDIOM_LIMIT: IDIOM_RULES may only match predefined policy entries. SEQUENCE_INTEGRATOR must not infer new idioms.
    IF NOT_RECOGNIZED → apply UNKNOWN_COMBINATION rule
  LOGIC:
    IF elements have different INTERPRETATION → COMBINATION_FLAG = YES
    IF COMBINATION is known as IDIOM (in IDIOM_REGISTRY) → IDIOM_FLAG = YES
    IF COMBINATION is known as IDIOM but not in IDIOM_REGISTRY → UNKNOWN_COMBINATION_FLAG = YES
    IF COMBINATION creates epoch conflict → EPOCH_CONFLICT_FLAG = YES
    IF COMBINATION_FLAG = YES AND IDIOM_FLAG = NO → apply UNKNOWN_COMBINATION_RULE
  UNKNOWN_COMBINATION_RULE:
    DEFAULT_ACTION: no modification (BASE_ACTION remains unchanged)
    ACTION_RATIONALE: "unknown combination, no specific rule"
    OUTPUT_WARNING: UNKNOWN_COMBINATION_DETECTED
    IF IDIOM_REGISTRY is empty:
      IDIOM_FLAG = NO
      UNKNOWN_COMBINATION_FLAG = YES if COMBINATION_FLAG = YES
      BASE_ACTION remains unchanged
      OUTPUT_WARNING = IDIOM_REGISTRY_EMPTY
    NOTE: runtime may apply additional analysis if needed
  EXAMPLE: 💀😭 = IDIOM "very funny" → IDIOM_FLAG = YES, apply IDIOM_ACTION
  EXAMPLE: 💀☠️ = EPOCH_CONFLICT → EPOCH_CONFLICT_FLAG = YES
  EXAMPLE: 💀🔥 = unknown combination → UNKNOWN_COMBINATION_FLAG = YES, no modification
  NOTE: COMBINATION_ANALYSIS does not create new semantics — only classifies known combinations
  FORMULA: IDIOM_MATCH ≠ NEW_SEMANTIC_INTERPRETATION
  FORMULA: UNKNOWN_COMBINATION ≠ NEW_IDIOM

STAGE_4: EPOCH_CONFLICT_ROUTING
  INPUT: EPOCH_SEQUENCE_CONTEXT + EPOCH_CONFLICT_RULES
  ACTION: routing epoch conflict (not resolution)
  LOGIC:
    IF EPOCH_CONFLICT_FLAG = YES → apply EPOCH_CONFLICT_RULES
    EPOCH_CONFLICT_ROUTING_PRIORITY:
      1. PLATFORM_SPECIFIC (if rule exists for this platform — highest priority)
      2. CONTEXT_GATE (if context unambiguously determines epoch)
      3. RECENCY (newer epoch dominates if no context)
      4. AMBIGUITY (if conflict not resolved → AMBIGUITY_FLAG = YES)
    RULE_1: PLATFORM_SPECIFIC — platform rules have priority
    RULE_2: CONTEXT_GATE — determine dominant epoch by context (platform, cohort)
    RULE_3: RECENCY — newer epoch dominates (if no context)
    RULE_4: AMBIGUITY — if conflict not resolved → AMBIGUITY_FLAG = YES
  OUTPUT: ROUTING_EPOCH_CONTEXT or UNRESOLVED
  NOTE: EPOCH_CONFLICT_ROUTING does not determine which epoch is "correct" — only selects routing context
  NOTE: ROUTING_EPOCH_CONTEXT does not overwrite ACTIVE_EPOCH in original elements
  NOTE: RULE_3 (RECENCY) is a simplified fallback within ROUTING_PRIORITY and does not override the Higher_epoch_suppresses_lower principle from SPEC_FOUNDATION. If DORMANT_EPOCHS data is available, it takes priority over simple RECENCY.
  FORMULA: ROUTING_EPOCH_CONTEXT ≠ ACTIVE_EPOCH_REWRITE
  FORMULA: EPOCH_CONFLICT_ROUTING ≠ EPOCH_TRUTH_DECISION

STAGE_5: ACTION_SELECTION
  INPUT: results of STAGE_2–4 + SEQUENCE_INTEGRATOR_POLICY
  ACTION: selecting RUNTIME_ACTION_REQUEST
  LOGIC:
    BASE_ACTION: ACTION_MAP[SEQUENCE_RISK_LEVEL] (as in INTEGRATOR_TEMPLATE)
    INTENSITY_MODIFIER: if INTENSITY_FLAG = YES → modify ACTION
    COMBINATION_MODIFIER: if COMBINATION_FLAG = YES → modify ACTION
    EPOCH_CONFLICT_MODIFIER: if EPOCH_CONFLICT_FLAG = YES → modify ACTION
    FINAL_ACTION: apply modifiers in MODIFIER_PRECEDENCE order
  MODIFIER_PRECEDENCE:
    PRIORITY_1: EFFECT_FIELDS_INVALID / SEQUENCE_OUTPUT_INVALID (automatic rejection)
    PRIORITY_2: EPOCH_CONFLICT_UNRESOLVED (epoch conflict — highest priority)
    PRIORITY_3: SEQUENCE_AMBIGUITY = YES (ambiguity requires review)
    PRIORITY_4: CRITICAL risk
    PRIORITY_5: INTENSITY_HIGH / SPAM suspicion
    PRIORITY_6: KNOWN_IDIOM
    PRIORITY_7: BASE_ACTION (default base action)
  MODIFIER_APPLICATION:
    RULE_1: Apply modifiers in priority order
    RULE_2: If modifiers conflict → ACTION_MODIFIER_CONFLICT = YES
    RULE_3: If ACTION_MODIFIER_CONFLICT → route to HUMAN_REVIEW / INTEGRATOR_INSTANCE
    RULE_4: Do not apply conflicting modifiers automatically
  MODIFIERS:
    INTENSITY_LOW: no modification, ACTION_RATIONALE += "intensity_low"
    INTENSITY_MEDIUM: BASE_ACTION + RISK_ESCALATION (+1 level), ACTION_RATIONALE += "intensity_medium"
    INTENSITY_HIGH: BASE_ACTION + RISK_ESCALATION (+2 levels), ACTION_RATIONALE += "intensity_high"
    INTENSITY_CRITICAL: BASE_ACTION → FLAG_FOR_REVIEW (spam suspicion), ACTION_RATIONALE += "intensity_critical_spam"
    COMBINATION_IDIOM: apply IDIOM_ACTION from COMBINATION_RULES, ACTION_RATIONALE += "known_idiom"
    EPOCH_CONFLICT: BASE_ACTION + AMBIGUITY_FLAG = YES, ACTION_RATIONALE += "epoch_conflict_unresolved"
    ACTION_MODIFIER_CONFLICT: HUMAN_REVIEW, ACTION_RATIONALE += "modifier_conflict_detected"
  NOTE: ACTION_SELECTION forms advisory request, not mandatory action

STAGE_6: OUTPUT_ASSEMBLY
  INPUT: all results of STAGE_1–5
  ACTION: assembling RUNTIME_ACTION_REQUEST
  CHECK_1: RUNTIME_ACTION_REQUEST is defined
  CHECK_2: ACTION_RATIONALE is not empty
  CHECK_3: SEQUENCE_INTEGRATOR_LIMITATION_NOTE is present
  RETURN: RUNTIME_ACTION_REQUEST or ERROR_STATUS
  NOTE: STAGE_6 does not modify RUNTIME_ACTION_REQUEST after assembly

STAGE_7: FINALIZATION_CLEANUP_BEFORE_SESSION_CLOSE
  INPUT: RUNTIME_ACTION_REQUEST or ERROR_STATUS (assembled in STAGE_6)
  ACTION: checking for residue absence (AFTER_RUN_RESIDUE: FORBIDDEN)
  CHECK_1: temporary data is cleared
  CHECK_2: SEQUENCE_INTEGRATOR_POLICY is not cached (SESSION_ONLY)
  CHECK_3: SEQUENCE_OUTPUT is not cached between sessions
  OUTPUT: CLEANUP_CONFIRMATION
  NOTE: STAGE_7 executes after OUTPUT assembly, but before session close
  NOTE: STAGE_7 does not modify RUNTIME_ACTION_REQUEST
  NOTE: STAGE_7 does not affect the result returned in STAGE_6

SEQUENCE_INTEGRATOR_POLICY_MODEL:

SEQUENCE_INTEGRATOR_POLICY:
  ABSTRACT: SEQUENCE_INTEGRATOR_POLICY defines sequence adaptation rules
  STRUCTURE:
    INTENSITY_RULES:

      DOMAIN: medical / legal / educational
